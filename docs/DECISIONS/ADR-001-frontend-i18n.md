# ADR-001 Frontend I18n Strategy

## 状态

Accepted

## 背景

桌面端当前所有用户可见文案均以内嵌英文字符串存在于 React 组件内，不满足以下新要求：

- 首批支持中文与英文
- 默认跟随系统语言
- 用户需要在应用内显式覆盖语言选择
- 后续新增页面和功能必须避免再次出现中英混杂或散落硬编码

项目当前技术栈为 `React 19 + MUI + Zustand + Tauri 2`，并且尚未接入第三方 i18n 框架。

## 决策

前端采用轻量、自研、类型安全的国际化方案，而不是立即引入 `i18next` 等重型依赖。首版方案包含以下约束：

1. 支持的语言集合固定为：
   - `system`
   - `zh-CN`
   - `en`
2. 持久化存储“语言偏好”而不是直接存储最终语言：
   - `system` 表示始终根据当前系统语言重新解析
   - `zh-CN` / `en` 表示用户手动覆盖
3. 实际生效语言在前端运行时解析：
   - 优先读取 `navigator.languages`
   - 回退读取 `navigator.language`
   - 对非受支持语言做语言族映射，如 `zh-* -> zh-CN`
   - 无法识别时回退到 `en`
4. 翻译资源集中存放在前端 `i18n/messages` 中，按领域分组管理，避免散落在页面内
5. `en` 作为基准语言定义完整消息结构，其他语言必须与其保持同构
6. 应用通过统一 `I18nProvider + useI18n()` 暴露：
   - `locale`
   - `preference`
   - `setPreference()`
   - `t(key, params?)`
7. 所有新增用户可见文案必须通过翻译层获取，禁止在组件中继续新增硬编码英文文案
8. `Settings` 页面提供语言设置入口，展示“跟随系统 / 简体中文 / English”
9. 生效语言变更时同步更新 `document.documentElement.lang`

## 方案细节

### 语言解析

- `system` 偏好不写死某一语言，而是在应用启动和页面刷新时根据 WebView 暴露的系统语言动态解析
- 当前桌面端无需新增 Rust 命令；系统语言默认从 WebView/Navigator 获取即可满足需求

### 翻译组织

- 使用嵌套对象按领域组织键名，如：
  - `app.shell.startProxy`
  - `settings.language.followSystem`
  - `sessions.explorer.empty.title`
- 动态文案统一使用插值参数而不是字符串拼接
- 列表步骤、风险说明、按钮文案等也纳入消息资源，不保留额外英文常量表

### 类型安全

- 基于英文消息对象推导翻译 key 类型
- 通过编译期约束确保中文资源不缺 key
- 公共帮助函数负责插值与 locale 解析，业务组件只消费 `t()`

### 状态与存储

- 使用 `Zustand persist` 保存语言偏好
- 首次启动默认值为 `system`
- 当用户选择 `system` 时，不额外缓存解析结果，避免系统语言变化后失效

## 备选方案

### 方案一：引入 `i18next + react-i18next`

优点：

- 生态成熟
- 支持命名空间、复数、异步加载

缺点：

- 当前仅有双语和本地资源，接入成本偏高
- 会增加额外抽象和依赖体积
- 对现阶段桌面端规模而言收益不明显

结论：暂不采用。

### 方案二：只做简单字典映射，不提供 Provider 和持久化偏好

优点：

- 实现最快

缺点：

- 无法支持系统语言跟随与用户覆盖并存
- 动态文案容易再次散落
- 不利于后续扩展更多页面

结论：不采用。

## 影响

正向影响：

- 统一前端文案入口，降低后续多语言扩展成本
- 避免页面间出现中英混杂
- 为设置页、格式化展示和后续更多语言扩展提供稳定边界

成本与限制：

- 首次接入需要批量替换现有用户文案
- 当前插值能力只覆盖本项目所需场景，复杂复数规则后续如有需要再引入专门库

## 落地要求

- 文档先于代码更新
- 首批改造覆盖现有桌面端所有可见核心文案
- 新增或修改文案时必须同时更新中英文资源
