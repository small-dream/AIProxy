# ADR-011：Agent 控制使用进程级、动作指纹绑定的限时授权

- 状态：`Accepted`
- 日期：`2026-11-04`
- 关联文档：`docs/PRD.md`、`docs/ARCHITECTURE.md`、`docs/API_SPEC.md`、`docs/UI_GUIDELINES.md`、`docs/PAGE_BLUEPRINTS.md`、`docs/AGENT_ACCESS_PERMISSION_UX_PLAN.md`、`docs/DECISIONS/ADR-006-local-mcp-agent-access.md`、`docs/DECISIONS/ADR-007-agent-control-ipc.md`

## 背景

静态布尔权限要求用户在任务开始前预判 Agent 未来需要什么。为了避免中断，用户容易长期开启“完整控制”，但页面又无法解释一次批准究竟覆盖哪个客户端、哪个动作、哪些参数以及何时失效。

现有 MCP 客户端没有稳定提供对话或任务 ID，AIProxy 也无法可靠判断“任务何时结束”。因此本版不能承诺任务级授权或任务结束自动失效。需要一个可撤销、可审计、在应用进程退出后不恢复的授权层，同时保持现有静态权限的兜底作用。

## 备选方案

1. **只保留长期布尔权限**：实现简单，但持续制造过度授权和频繁切换；否决。
2. **按“最近一次授权”模糊复用**：用户体验顺滑，但并发对话或参数变化时可能把 A 的批准用于 B；否决。
3. **仅用客户端名称作为身份**：配置简单，但同一客户端可同时运行多个对话或进程，无法隔离授权；否决。
4. **稳定 sidecar 实例 + 客户端身份 + 能力 + 动作指纹 + 限时额度**：能够在现有协议下明确复用边界，并可通过撤销和审计收尾；采纳。

## 决策

### 1. 三种用户可见状态

每项能力统一表达为：

- `禁止`：直接拒绝，不允许发起审批。
- `请求时询问`：静态权限关闭时，Agent 可为具体动作请求限时授权；静态权限开启后不再弹卡。
- `始终允许`：静态布尔权限开启，Agent 直接调用。

后端继续保留布尔权限与 `grantRequestPolicy` 两个兼容字段，但 UI 不得把它们呈现成两套矩阵。高风险能力默认 `禁止`；从 `禁止` 改为 `请求时询问` 或 `始终允许` 都必须经过高风险二次确认。

默认 `禁止` 的能力为：`controlSystemProxy`、`manageCertificates`、`deleteSessions`、`manageScripts`、`manageCrossHostMappings`、`manageUserAutomation`、`manageGlobalAutomation`。其余可用能力默认 `请求时询问`。

### 2. 授权身份和动作绑定

一次授权必须同时匹配以下字段：

- sidecar 进程内稳定的 `agentInstanceId`；
- MCP 客户端名称与版本；
- 能力；
- 动作指纹。

控制操作的指纹来自完整操作 DTO 的确定性序列化。控制类请求还在 `ControlRequest.actionFingerprint` 中携带该指纹，桌面端会重新计算并比较；参数变化、目标 Session 变化或请求方法变化均不能复用旧批准。

读取类能力使用能力与授权范围生成指纹，例如 Body 读取至少绑定 Session ID；同一 sidecar 进程被多个对话共享时，它们共享同一份限时授权，这是本版明确接受的限制，不宣称对话级隔离。

### 3. 授权额度

- `once`：批准后 60 秒内可用 1 次。
- `fifteenMinutes`：批准后 15 分钟内最多 50 次。
- 非幂等动作与高风险能力只提供 `once`，包括非幂等重放、删除、证书信任撤销、系统代理、用户自动化、脚本、跨 host 映射和全局自动化。
- 同一 sidecar、客户端、能力与指纹的重复请求合并到同一个 pending 授权，用户只审批一次，原工具调用继续等待。
- 审批等待上限 30 秒；拒绝后同一授权键冷却 60 秒，冷却期内重复请求不再弹卡。
- 临时授权文件最多保留 200 条记录，超出时淘汰最旧记录。

### 4. 授权必须先预占，再执行

授权消费是原子预占：

1. 桌面端验证实例、客户端、能力、指纹、状态和剩余次数。
2. `mark_executing` 在锁内扣减一次额度并置为 `executing`。
3. 仅在预占成功后才执行动作。
4. 成功或普通失败后，可重复授权恢复为 `approved`；一次性授权耗尽后进入 `expired`。
5. 响应丢失、桌面端写回响应失败或审计写入失败后，结果标记为 `unknown`，不得自动重试。
6. 运行期间被撤销或到期的授权不会被迟到的成功结果“复活”。

这保证两个并发请求不能共用同一次一次性额度，也避免对可能已产生外部副作用的动作盲目重试。

### 5. 进程级存储与失效

- 临时授权写入 `<data-dir>/agent-grants.json`，Unix 权限 `0600`，Windows 限制为当前用户 ACL。
- 授权只在当前桌面应用进程内有效；应用启动时先清空文件与内存状态，不恢复任何 pending、approved 或 executing 授权。
- sidecar 退出或重启会生成新的 `agentInstanceId`，旧授权无法继续使用。
- 这不是“任务结束自动失效”。无法可靠识别任务结束时，UI 与帮助文档只能称其为“限时授权”。

### 6. 审批入口与撤回

- 待审批对话框由 `AppShell` 全局挂载，不要求用户先打开 Settings；同时发送系统通知。
- Settings 的“待审批与限时授权”列表负责查看、单条撤销和刷新，不是唯一审批入口。
- 用户批准、拒绝、超时、取消、执行、失败、未知结果和撤销都会产生可见状态。
- `revoke_agent_control_permissions` 立即落盘关闭全部控制与自动化权限、把控制类的请求策略改为 `deny`、清除全部临时授权，并保留读取权限。
- 普通权限编辑仍进入草稿；只有“立即收回控制”绕过草稿立即生效。
- 撤回授权只停止后续调用，不撤销已经执行的请求、已启动的抓包、已接管的系统代理、已信任的证书或已创建的 Agent 规则与自动化资源。结果必须返回残留副作用，并提供停止抓包、恢复系统代理、管理证书和查看 Agent 资源的入口。

### 7. 双端复核

- sidecar 在发起控制请求前读取配置，决定直接执行、请求授权或拒绝。
- 桌面端在 IPC 边界重新校验 Agent Access 启用状态、token、协议版本、权限、请求策略、授权实例/客户端/能力/指纹、剩余次数和审计可写性。
- 等待桌面写锁期间会再次执行预检；排队期间撤销权限会使请求在执行前失败。
- 控制协议升级为 v2，新增 `RequestAgentGrant` 与 `ConsumeAgentGrant`；桌面端和 sidecar 必须同步升级。

## 错误码

- `GRANT_POLICY_DENIED`：能力未开启静态权限，且请求策略为禁止。
- `GRANT_REQUEST_FAILED`：创建或解析授权请求失败。
- `GRANT_CONSUME_FAILED`：读取类能力的授权消费失败。
- `APPROVAL_REQUIRED`：需要审批，或批准不覆盖当前动作。
- `APPROVAL_INVALID`：授权不存在、已失效、额度耗尽或绑定不匹配。
- `APPROVAL_FINGERPRINT_MISMATCH`：动作参数已经变化，必须重新审批。
- `APPROVAL_DENIED`：用户拒绝。
- `APPROVAL_TIMEOUT`：等待审批超时。
- `APPROVAL_CANCELLED`：授权被撤销或等待被取消。
- `AUDIT_UNAVAILABLE`：审计不可写；动作可能已经完成时不能盲目重试。

## 后果

- 用户可以在具体动作发生时批准一次或 15 分钟，而不必预先长期开启高风险权限。
- 授权与 sidecar 进程同寿命，应用重启后必须重新批准；这是安全选择，也会带来跨重启重新审批的成本。
- 自动化资源生命周期与授权有效期分离。15 分钟授权到期不会删除此前创建的持久资源，临时资源的 TTL 也不会因为授权仍有效而延长。
- 同一 sidecar 被多个对话共享时，同一动作范围内的授权可被共享；若要支持对话级隔离，需要 MCP 客户端提供稳定 conversation/task ID。
- 直接连接本地 IPC 的同用户进程仍受桌面端双重校验和授权指纹约束，但本机同用户进程的信任边界仍高于跨用户隔离。

## 回滚

- 功能回滚：移除审批对话框与 grant store，恢复静态权限；sidecar 与控制协议同时回退到 v1。旧版桌面端会拒绝 v2 请求并提示同步升级/重启。
- 配置回滚：忽略 `grantRequestPolicy` 后，能力只由静态布尔权限决定；`deny` 不会错误地开启能力。
- 安全回滚：先调用 `revoke_agent_control_permissions` 关闭控制并清理临时授权，再降级版本；已执行的抓包、系统代理、证书和 Agent 资源仍需单独清理。
