## 4. 🟠 高危

### H1 ✅ 脚本规则改写响应体后，明文字节仍在原 `content-encoding` 下发出 → 客户端收到损坏响应

- **位置**：`crates/proxy-core/src/rules/script.rs:70-84`（`build_script_response` 调 `body_text_and_base64` → `build_body_reference` 解码）；`:144-160`（`apply_script_response_to_runtime` 写回字节、按脚本头重建 header）
- **类别**：协议正确性 / 核心功能失效
- **确认依据**：脚本通过 `body_text_and_base64` 拿到的是**已解压**的 body（`http_io.rs:391-393` 的 `decode_body_bytes` 会先 gzip/deflate/br 解码再交给脚本）。脚本 `setText(...)` / `setJson(...)` 返回后，`apply_script_response_to_runtime` 用 `bytes_from_script_body` 取 `text.into_bytes()`（已是明文字节），并通过 `header_map_from_script_headers` 从脚本返回的头重建 `response_headers`。由于 JS 桥（`js_bridge.rs:144`）`__aiproxyClone(payload.response)` 完整克隆了原响应头，其中包含 `content-encoding: gzip`，只要脚本没有显式 `removeHeader("content-encoding")`，该头就会被原样保留。
- **现象**：对命中 `onResponse` 脚本的 gzip/br/deflate 响应做任何 body 改写，客户端会收到 `Content-Encoding: gzip` + **明文** body → 浏览器/上游解码器报 `Z_DATA_ERROR` / 下载损坏。这是脚本规则作为核心功能的正确性缺陷。
- **对比**：rewrite 路径（`rewrite.rs:48-55` `strip_plain_body_edit_header_entries`）在改写 body 时**会**剥离 `content-encoding/content-md5/digest/etag`；脚本路径没有等价处理。
- **修复方向**：在 `apply_script_response_to_runtime` / `apply_script_request_to_runtime` 写回 body 后，调用与 rewrite 一致的 `strip_plain_body_edit_header_entries`（请求侧同理）。补测试：gzip 响应 + `onResponse` 改 body，断言发出给客户端的响应无 `content-encoding` 且 body 可读。
- **置信度**：✅

### H2 ✅ 每条脚本 hook 每次命中都 spawn 一个裸 OS 线程，无线程池/并发上限 → 高并发下线程/fd 耗尽

- **位置**：`crates/rule-engine/src/execute.rs:71-87`（`std::thread::spawn`）；调用点 `crates/proxy-core/src/http_proxy.rs:309 / 446 / 775`（`apply_request_script_rules` / `apply_response_script_rules` 在 async `handle_http_request` 中**同步**调用）
- **类别**：资源耗尽 / DoS
- **确认依据**：每次 `run_script_in_thread` 都新建一个 `rquickjs::Runtime`（独立堆 + GC + interrupt handler）并完整 eval bridge + 用户模块。`apply_*_script_rules` 对**每个匹配规则 × 每个 in-flight 请求**触发一次。并发请求 × 规则数 N×M 即同时存活的 OS 线程数，而连接信号量 `MAX_CONCURRENT_CONNECTIONS=1024` 只限 socket，不限脚本线程。
- **现象**：真实代理负载或一次突发下，每个线程持有一个 16MB 级 QuickJS 堆，迅速触及进程线程/fd 上限或 OOM；同时线程以 `recv_timeout` 阻塞 async task 最长 500ms，单个慢脚本拖累整个 Tokio worker。
- **修复方向**：用 `tokio::task::spawn_blocking` + 全局有界线程池（如 `rayon` 或自建 `Runtime` 池 + Semaphore 限并发），或复用预创建的 QuickJS Runtime。至少加一个全局脚本并发上限。
- **置信度**：✅

### H3 ✅ macOS 还原系统代理时不会重新启用原 Auto Proxy URL (PAC)，企业网用户失去自动代理配置

- **位置**：`apps/desktop/src-tauri/src/system_proxy/macos.rs:275-288`（`restore_auto_proxy_url_settings`）
- **类别**：核心功能失效 / 跨平台正确性
- **确认依据**：
  ```rust
  if let Some(url) = snapshot.url.as_deref() {
      run_networksetup("-setautoproxyurl", &[service_name, url])?;
      if !snapshot.enabled {
          set_auto_proxy_url_state(service_name, false)?;
      }
      return Ok(());
  }
  set_auto_proxy_url_state(service_name, false)
  ```
  `apply_system_proxy_settings_with_snapshot`（`:139`）会先 `set_auto_proxy_url_state(..., false)` 关掉 PAC。还原时若快照 `enabled == true` 且有 `url`，本函数只写入了 URL，却只在 `!enabled` 分支里调 `set_auto_proxy_url_state(false)`——`enabled == true` 时**从不调** `set_auto_proxy_url_state(service_name, true)`，PAC URL 被写入但保持关闭状态。
- **现象**：依赖 PAC 文件的企业/公司网用户，在「开启 AIProxy 系统代理 → 关闭（或退出 App）」循环后，PAC 永久保持关闭，网络异常，直到手动在系统设置里重新启用。
- **修复方向**：在 `enabled == true` 分支显式 `set_auto_proxy_url_state(service_name, true)?;`。补平台实测。
- **置信度**：✅

### H5 ✅ `create_workspace` / `update_workspace` 吞掉 DB 持久化错误并返回成功，重启后工作区消失

- **位置**：`apps/desktop/src-tauri/src/commands/workspaces.rs:59-67`（`create_workspace`）；`:154-169`（`update_workspace`）
- **类别**：数据丢失 / 错误处理

  let placeholders: Vec<String> = run_ids.iter().enumerate()

## 5. 🟡 中危

### M1 ✅ WS 续帧（Continuation）被独立解码为 UTF-8，分片跨多字节边界时文本丢失/错位

- **位置**：`crates/proxy-core/src/ws.rs:356-357`（`build_ws_message`）；relay 未做重组：`:610 / :668` 对每个 frame 直接调 `build_ws_message`，无 FIN 累积缓冲
- **确认依据**：
  ```rust
  let payload_text = if frame.opcode == WsOpcode::Text || frame.opcode == WsOpcode::Continuation {
      String::from_utf8(frame.payload.clone()).ok()
  } ...
  ```
  Continuation 帧是某个分片消息的一个片段。单独做 UTF-8 解码：(a) 当分片边界切到一个多字节码点中间时 `from_utf8` 失败返回 `None`，文本直接丢；(b) 即便成功，也只是把某个片段当作完整文本展示。对「忠实抓取并展示 WS 流量」的工具，大型/分片文本消息的文本被静默丢弃或截断，是正确性缺陷。
- **修复方向**：按 RFC 6455 重组——记录起始 opcode（Text/Binary）+ 累积 Continuation payload 直到 `FIN=1`，再统一解码为一条 `WsMessageData`。现有 `frame.fin` 字段已具备条件，只是没用起来。
- **置信度**：✅

### M2 ✅ h2 连接池在 `send_request` 成功后读取 body 出错时不驱逐，下个请求复用坏连接再次 502

- **位置**：`crates/proxy-core/src/upstream.rs:195-223`
- **确认依据**：驱逐（`p.evict_key(&key).await`）只在 `h2_sender.send_request(...)` 失败分支（`:197-205`）。`send_request` 成功后 `:223` 调 `build_upstream_response_from_hyper` 读 body；若读 body 期间 h2 流出错（`RST_STREAM` 或连接死掉），返回 `Err` 但**不驱逐**。下次同 host 请求复用这条坏掉的池连接再次失败。h1 路径每请求新建连接，不受影响。
- **现象**：经典的「keep-alive 空闲后第一个请求失败」放大——一次 body 读取错误后，后续请求连续 502 直到该 key 自然淘汰。
- **修复方向**：把「body 读取错误」也纳入驱逐路径；或统一在 `forward_request` 出错时按 host:port 驱逐池。
- **置信度**：✅

### M3 ✅ h2 池无活性探活，半开/TCP-RST 的连接被直接复用 → 空闲后首个请求偶发 502

- **位置**：`crates/proxy-core/src/upstream_pool.rs:64-80`（fast-path 仅查 `is_closed()` + idle_timeout）
- **确认依据**：`is_closed()` 只反映本地 `SendRequest` 是否**已观察到**连接结束，检测不到 NAT/中间盒静默丢弃的半开 socket。`idle_timeout=60s` / eviction `max_idle=120s` 窗口内被挂掉的连接，下次取用时被发出去 → `send_request` 失败 → 502，且无自动重试。
- **现象**：对空闲 keep-alive 主机的请求有可观测比例的假性 502（与 M2 叠加放大）。
- **修复方向**：取用前发一个轻量探活（如 h2 PING），或在 `send_request` 失败时**降级重建一条新连接重试一次**（结合 M2 的驱逐）。
- **置信度**：✅

### M4 ✅ WS / wss 升级握手响应头用 `String::from_utf8` 严格校验，含任意非 UTF-8 字节即转 502

- **位置**：`crates/proxy-core/src/connect.rs:499-528`（`read_http_response_head`）；`ws_upgrade.rs:262-279`（`parse_upstream_response_head`）复用同一逻辑
- **确认依据**：
  ```rust
  let head = String::from_utf8(head).map_err(|e| format!("response head utf8: {e}"))?;
  ```
  HTTP 头字段值在技术上是不透明字节（obs-text / 百分号编码 / 非 ASCII，如 legacy `Content-Disposition: filename=` 的原始字节，或 Latin-1 状态原因）。任何非 UTF-8 字节都会让 `read_http_response_head` 返回 `Err`，被升级路径转成合成 502——即便上游发了完全合法的 101。
- **现象**：上游 101 响应携带非 UTF-8 字节（如 `Sec-WebSocket-Protocol` 回显非 ASCII）时，合法 WS 升级被误报为 502。
- **修复方向**：按字节解析头部，日志/展示用 lossy 解码；只有协议关键行（status line / 头名）才需要 ASCII。
- **置信度**：✅

### M5 ✅ WS 注入通道为 unbounded，注入方无背压，可撑大 relay 任务/注册表内存

- **位置**：`crates/proxy-core/src/ws.rs:545-548`（relay 签名收 `&mut UnboundedReceiver`）；注册 `:713-748`（`unbounded_channel` + 全局 registry 持有 `UnboundedSender` 整个会话期）
- **确认依据**：`inject_tx` 是 `UnboundedSender`，由全局 registry 在整个 WS 会话期间持有。任何 `registry.inject(...)` 调用（replay/inject API）可无上限入队；每个 `WsInjectRequest.payload: String` 大小任意。relay 的 `select!` 每轮只排空一个 inject，且每次 inject 还要做完整 mask 拷贝（`write_ws_frame`），队列只能以 socket 速度排空。
- **现象**：注入方比上游 socket 刷写快，或注入大 payload 时，会话期内内存无界增长。
- **修复方向**：改 bounded channel（容量如 64），`inject` 在满时返回 busy/丢弃。
- **置信度**：✅

### M6 ✅ DB N+1：洞察面板按 host 算 P95，每个 host 一次全表扫描 + 全量排序

- **位置**：`crates/db/src/insights.rs:264-279`（`compute_insights` 循环）；`:414-441`（`compute_host_p95` 单 host 全扫）
- **确认依据**：
  ```rust
  for hr in &host_rows {
      let p95 = compute_host_p95(conn, &hr.host, filter)?;   // 每个 host 一次全扫 + ORDER BY
      result.push(HostInsight { ... });
  }
  ```
  `by_host` LIMIT 50，最坏 50 次对 `session_summaries` 的 `ORDER BY duration_ms` 全扫（`host` 与 `duration_ms` 均无索引）。长寿装机上数万会话时，洞察面板 I/O 放大明显。
- **现象**：洞察面板在大数据量下变慢；DB mutex 期间占用更久。
- **修复方向**：一次性 `SELECT host, duration_ms FROM ... WHERE ...`，按 host 分组后在 Rust 内做 nearest-rank 百分位（O(n) 一趟）。
- **置信度**：✅

### M7 ✅ `session_details` 缺少 `session_summary_id` 索引，热查与级联删除走全表扫

- **位置**：`crates/db/src/schema.rs:132-151`（建表 + FK，无 index）；查询 `crates/db/src/sessions.rs:261`（`WHERE session_summary_id=?1`）；删除 `:368-373`（`DELETE FROM session_details WHERE session_summary_id IN (...)`）
- **确认依据**：同族的每个子表（`ws_messages`→`idx_ws_messages_session`、`script_runs`→`idx_script_runs_session`、…）都有配套索引，唯独 `session_details` 漏建。点击会话列表项的详情查询、以及历史清理路径的级联删除都全表扫。
- **现象**：大型 DB 上详情打开变慢；后台清理的 `IN (...)` 每批全表扫。
- **修复方向**：`CREATE INDEX IF NOT EXISTS idx_session_details_session ON session_details(session_summary_id);`（加到 `schema.rs`，随 migrate 上线）。
- **置信度**：✅

### M8 ✅ TLS host 证书缓存按 hostname 单键，根 CA 轮换后仍可能下发旧签发证书（`clear_host_cache` 是死代码）

- **位置**：`crates/tls-manager/src/resolver.rs:31-96`（`resolve` 命中缓存直接返回，不校验签发者）；`storage.rs:248`（`clear_host_cache` 定义）；全仓 grep：`clear_host_cache` **无任何调用方**
- **确认依据**：缓存是 `LruCache<String/*hostname*/, Arc<CertifiedKey>>`，只在 `clear_host_cache()` 被调时失效，而该方法无人调用。用户点「重新生成根 CA」（`commands/certificates.rs:398-428` `force_regenerate=true`）换新 CA 后，只要旧 `CertStorage` 的 `Arc<Mutex<host_cache>>` 因任一 clone 仍存活（如仍在飞的连接、缓存的长生命周期 `TlsManager` 值），旧签发的叶子证书最长可在缓存里留到 `DYNAMIC_CERT_VALIDITY_YEARS`（1 年），违背轮换目的。
- **现象**：根 CA 轮换后，部分客户端仍拿到旧根签发的证书，信任链预期被破坏。
- **修复方向**：`generate_root_certificate_impl` 强制重生成时调 `clear_host_cache()`；或让缓存 key 包含根 CA 指纹，轮换后自然失效。
- **置信度**：✅（轮换必失效；是否实际命中旧缓存取决于 Arc 存活情况，故未达 high）

### M9 ✅ Linux 信任检查把多证书 bundle 的所有 base64 拼接后一次性哈希 → Debian/Ubuntu 上永久误报「未信任」

- **位置**：`crates/tls-manager/src/trust.rs:167-257`（`is_trusted_linux`）；`check_dir(live_dir, false)`（`:252`）扫 `/etc/ssl/certs/`
- **确认依据**：处理 `ca-certificates.crt` 这类合并 bundle 时，代码剥离所有 `-----...-----` 围栏行，把**整文件所有证书**的 base64 拼成一个大串，base64 解码整个 blob，再算一个 SHA-1。这永远不等于单张证书的指纹。
- **现象**：Debian/Ubuntu 默认把受信根装进 bundle，UI 会永远把 AIProxy 根 CA 报为「未信任」，即便已成功安装，误导用户反复重装。这正是第二轮 N2「待实测」项——本次确认代码路径对 bundle **必然**误判。
- **修复方向**：按 `-----END CERTIFICATE-----` 切分 bundle，逐张哈希比对；或用 `x509-parser` 迭代证书。
- **置信度**：✅（机制确定；是否在具体发行版命中取决于 `update-ca-certificates` 是否额外生成单证书 `.0` 文件）

### M10 🔶 节流「整 body 单次 sleep」+ mock 与上游路径 body 长度基准不一致

- **位置**：`crates/proxy-core/src/rules/throttle.rs:77-97`（`apply_response_throttle` 单次 `sleep`）；调用 `http_proxy.rs:904-905`（上游路径传 `response_body_size_bytes` 全量）vs `:458-459`（mock 路径传 `mock_response.response_body.len()` 截断后内存长度）
- **确认依据**：节流按整 body 一次性 `sleep(transfer_delay_ms)`，不是随字节流出增量限速。对大 body（如 200MB @ 1Mbps ≈ 27 分钟）会**先完整读取/落盘缓冲、再整体 sleep、再发首字节**（大响应会 spool 到磁盘，见 `upstream.rs:521-539`，之后在 `http_proxy.rs:938-946` 读回），连接/任务全程占用。同时 mock 与上游两路用不同 body 长度基准，trace 上的有效延迟不可比。
- **现象**：大文件下载节流时连接看似长时间挂起；mock vs 上游节流统计口径不一致。
- **修复方向**：随字节流增量节流（边读边 sleep 边发）；统一基准（都用真实 wire size）。
- **置信度**：🔶（「整 body 单 sleep」可能是当前有意设计；基准不一致是确定缺陷）

### M11 🔶 `upsert_collection` 父校验/环检测在写事务外做，与 `move_collection` 不对称（事务卫生，非当前可触达 TOCTOU）

- **位置**：`crates/db/src/collections.rs:46-95`（`upsert_collection`：先 `ensure_collection_exists` + `would_create_cycle`，再裸 UPDATE/INSERT）；对比 `move_collection`（`:366-436`）同类校验**包在 `unchecked_transaction()` 里**
- **确认依据**：`api_collections.parent_id` 无 FK（`schema.rs:285`），引用完整性/无环完全靠应用层。`upsert_collection` 的校验与写未包在同一事务里。**但**当前 Tauri 命令层（`commands/collections.rs:308-315`）在调用 `upsert_collection` 期间全程持有全局 `Arc<Mutex<Connection>>`（连接在 `main.rs:103` 以单一 `Mutex<Connection>` 创建），即在单连接模型下校验与写之间连接始终被锁，TOCTOU 窗口**当前不可达**。真正的问题是事务卫生/一致性：与 `move_collection` 的事务化处理不对称，一旦未来引入连接池、`spawn_blocking` 重入或多写者，这份非事务化的校验+写即成为可触达的 TOCTOU。
- **修复方向**：把校验+写包进一个 `unchecked_transaction()`，与 `move_collection` 对齐（防御性 + 一致性，非紧急）。
- **置信度**：🔶（确定性缺陷是「非事务化」本身；当前不可达 TOCTOU）

### M12 🔶 WS 非 101 升级响应只回写 head 不回写 body，客户端拿到无 body 的响应头

- **位置**：`crates/proxy-core/src/connect.rs:280-495`（`handle_https_websocket_upgrade`）
- **确认依据**：上游返回非 101（如 403/404）时，本函数只 `write_all(response_head)` 然后无条件进 `relay_websocket_frames`，把剩余字节当 WS 帧解析。实际 HTTP 响应 body 被喂进 WS 帧解析器，首字节即失败，客户端收到 head 但无 body。hyper 升级路径（`ws_upgrade.rs`）处理正确（先读全 body），此 wss 变体没做。
- **现象**：目前该路径被标 `#[allow(dead_code)]`（项目走 hyper 升级路径），实际未命中；但若重新启用即破。
- **修复方向**：与 hyper 路径对齐，非 101 时先读全 body 再回写给客户端；或直接移除死代码避免误导。
- **置信度**：🔶（逻辑错误确定，但当前死代码未命中）

### M13 ✅ `respond()` 不短路，多次 `respond()` 与 respond 后继续 mutate 会静默合并

- **位置**：`crates/rule-engine/src/js_bridge.rs:175-193`（`respond` 仅赋值 `responseOverride`，不 return / 不设短路标志）；`:234-246`（hook 体仍跑到结束）
- **确认依据**：`respond()` 只写闭包变量，`Promise.resolve().then(runHook)` 仍把 `fn(ctx)` 跑完。`if (cond) ctx.respond({status:200,...}); ctx.respond({status:201,...});`（缺 `else`/`return` 的常见笔误）第二次静默覆盖第一次，无任何告警。respond 后继续 `ctx.request.setHeader(...)` 的改动也会进 result（请求阶段虽在 `apply_request_script_rules:225-237` 命中 override 分支后 `break`，但 result 早已算完包含这些无意义的 request mutation）。
- **现象**：用户「短路 mock」的语义意图（见测试 `supports_short_circuit_mock_responses`）实际未在 JS 层强制；多 respond / respond 后继续修改造成 trace 与结果困惑。
- **修复方向**：`respond()` 内置短路标志，hook 包装器检测到后停止后续执行（或至少 warn）；文档明确语义。
- **置信度**：✅

## 6. 🟢 低危（健壮性 / UX / 规范）

## 11. 复核补丁（2026-06-29）

针对第 10 节修复的复核，发现并修复了 2 个回归/不完整项。

### R1（复核 H1）：脚本 no-op 不应改写 body（H1 过度应用）

- **问题**：H1 的 `strip_plain_body_edit_headers` 无条件作用于每个返回 response/request 的脚本规则。但 JS 桥（`js_bridge.rs` `__aiproxyInvoke`）总是把克隆的 `ctx.request`/`ctx.response` 序列化回 Rust，`apply_*_script_rules` 对任何 `Some` 的返回都应用。结果：即使是只读/仅日志的 `onResponse` 脚本，也会把 gzip 响应解码→替换→剥离 `content-encoding`，改变了**所有**命中脚本的 wire 行为，而非仅 body 编辑。
- **确认**：`js_bridge.rs:253-261` 始终回传 request/response；`script.rs:296` 对 `Some` 无条件应用；`script.rs:161/140` 无条件剥离。
- **修复**：JS 桥在 hook 执行前后对 `ctx.request`/`ctx.response` 各做一次 `JSON.stringify` 快照比较（同时覆盖 body helper 调用与直接字段赋值 `ctx.request.url = ...`），**未变更时回传 `null`**；运行时错误 / skipped 分支也回传 `null`（不应用可能不完整的改动）。Rust 侧调用点已是 `if let Some`，故未变更时自然 no-op，content-encoding 不再被误剥离。
- **验证**：3 个新单测——no-op 脚本报 `request/response = None`；mutating 脚本（`setText`）仍报变更；直接字段赋值（`ctx.request.url = ...`）也被检测为变更。rule-engine 25 测试全过。

### R2（复核 M8）：运行中代理未刷新 TLS 配置（M8 不完整）

- **问题**：M8 仅 `clear_host_cache()` + 交换 AppState 的 TlsManager。但运行中的代理在 `start_proxy_server` 时捕获了 `Arc<TlsManager>`（`proxy.rs:145`），其 `ServerConfig` 内嵌的 `DynamicCertResolver` 仍持有**旧** `root_ca_sign_data`（`resolver.rs:12`）。清空缓存后，该 resolver 会用**旧根**重新签发 host 证书——轮换目的落空。M8 注释中「旧 resolver 会用新根重签」的前提是错误的。
- **确认**：`resolver.rs:48-51` 命中未命中时用 `self.root_ca_sign_data`（解析器自身字段）签发；`ServerConfig` 构造后不可变（rustls 约束）。
- **修复**：`generate_root_certificate_impl` 在安装新 TlsManager 后，若代理正在运行则**重启代理**（新增 `proxy::restart_proxy_if_running`，按当前 status 重建 `StartProxyInput` 调 `start_proxy_impl`，后者先关停旧 runtime 再启动）。重启是唯一正确选项——rustls `ServerConfig`/cert resolver 构造后不可变；既有 TLS 会话被中断符合预期（轮换会使客户端原先验证的信任锚失效）。重启失败时记 error 并返回 Err，代理保持停止。
- **验证**：`aiproxy-desktop` 编译通过；既有代理启停路径不变（`start_proxy_impl` 已是「先关后启」）。运行时重启行为需在桌面环境实测（涉及 Tauri async runtime + 系统代理重应用）。

### R3（复核 R2）：`generate_root_certificate` 不应 `block_on` 嵌套运行时

- **问题**：R2 把代理重启放在同步 `generate_root_certificate` 命令里，用 `tauri::async_runtime::block_on(restart_proxy_if_running(...))` 调用。该重启路径 await 了 shutdown/start，且可能跑在 Tauri 用于其 async 命令的同一 Tokio 运行时上，有嵌套运行时 panic 或阻塞 worker 的风险。
- **确认**：`certificates.rs:109` 命令为 `pub fn`（同步）；`certificates.rs:449` `block_on(...)` 在重启路径。
- **修复**：将 `generate_root_certificate` 命令与 `generate_root_certificate_impl` 都改为 `async fn`，重启改 `restart_proxy_if_running(...).await`，移除 `block_on`。async 命令由 Tauri 在其 async 运行时上调度，签名/注册（`generate_handler!`）/前端调用（已 `await invoke`）均无需改动。
