# 发布摘要

此目录保存每个 GitHub Release 面向用户的双语更新摘要，是发布说明和应用内更新说明的唯一内容来源。

## 文件命名与结构

- 每次发布都必须新增一个文件：`v<版本号>.md`，例如 `v0.1.19.md`、`v0.1.19-beta.1.md`。
- 文件名必须与 Git tag 完全一致。
- 文件必须包含 `## 更新内容` 和 `## What's new` 两个标题；两个部分都只描述用户可感知的变更。
- 以中文在前、英文在后的顺序编写。建议每种语言使用相同数量、语义对应的条目。

最小模板：

```md
# AIProxy v0.1.19

## 更新内容

- 说明本版本最重要、用户能直接感知的一项变更。
- 说明修复的问题及其用户影响；没有时不必凑条目。

## What's new

- Describe the most important user-visible change in this release.
- Describe a user-impacting fix when applicable; do not add filler items.
```

## 写作准则

- 先写“用户为什么值得更新”，按重要性排序；首条必须是本版本最重要的功能或改进。
- 使用简洁、明确且可验证的表达，优先说明结果与使用场景，而不是内部实现。
- 不要把 `chore`、重构、测试、依赖更新、格式化或提交信息原样写给用户；仅当它们造成可感知的兼容性、性能或安全影响时才说明影响。
- 破坏性变更、迁移要求、已知限制或安全更新必须同时用中英文清楚说明。
- 安装包格式、签名/公证状态和自动更新可用性不写入此文件。Release workflow 会根据实际构建产物自动追加可执行的安装与风险提示，避免说明与真实产物不一致。
- 应用内更新弹窗只按当前语言渲染对应小节（中文取 `## 更新内容`，英文取 `## What's new`），因此中英文条目必须保持语义一致，避免应用内与 Release 页面展示对不上。

## 发布约束

`release.yml` 仅允许从 Git tag 执行发布，并在发布前校验对应的摘要文件与双语标题。任一条件不满足，发布会失败且不会创建 GitHub Release。

推荐顺序：先在发版 PR 中更新版本号和本目录中的摘要文件，完成评审与质量门禁后，再从该 commit 创建并推送同名 tag。
