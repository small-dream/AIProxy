## 4. 🔴 安全

### S1 ✅ 已修复（70257ef） MITM 根 CA 私钥可能以过宽权限落盘

- **位置**：`crates/tls-manager/src/storage.rs:151-152`（`save_root_cert` 写 `root_key_path`）；同文件 `create_dir_all`（:139）同样未设权限
- **类别**：私钥保护失效 / 安全
- **确认依据**：`save_root_cert` 用 `std::fs::write(&self.root_key_path, key_pem)` 写入根 CA 私钥后，无任何 `set_permissions` 调用。全仓库 `grep` 无 `set_permissions` / `0o600` / `PermissionsExt`。文件最终权限取决于进程 umask（`std::fs::write` 按 `0666 & ~umask` 创建）：常见 umask `022` 下为 `0644`（其他用户可读），umask `077` 下才为 `0600`；`cert_dir` 权限同样不可控。是否实际可被其他用户读取，还取决于父目录是否对其他用户可遍历。
- **现象**：MITM 根 CA 私钥是整个代理信任链的根。当 umask 较松（典型 `022`）且 `cert_dir` 对其他用户可遍历时，同机其他用户或可遍历该目录的主体可读到私钥，进而签发被本机信任的任意 HTTPS 证书。
- **影响**：私钥保护边界不可控——是否实际泄露取决于 umask 与父目录权限，但代码未做收口，应视为应修。作为对标 Charles 的 HTTPS 抓包工具，根私钥应显式收紧权限，不应依赖运行时 umask。
- **修复方向**：写 key 后立即 `std::os::unix::fs::PermissionsExt::set_permissions(&self.root_key_path, from_mode(0o600))`（Unix，`#[cfg(unix)]`）；`cert_dir` 用 `DirBuilder::mode(0o700)` 创建；Windows 上用 ACL 限制为当前用户。补一个测试：写入后断言文件 mode 的 other 位无读/写（容错 umask 差异），避免未来回归。

### S2 ✅ 已修复（e7964c6） `save_text_file` 缺路径穿越防护

- **位置**：`apps/desktop/src-tauri/src/commands/files.rs:19-34`；对比同文件 `save_media_file` 已有 `reject_unsafe_write_path`
- **类别**：路径穿越 / 安全
- **确认依据**：`save_text_file` 的 `file_name` 来自前端，经 `next_available_export_path`（:117-118）做 `downloads_dir.join(file_name)`，**未校验** `file_name` 是否含 `..` / 路径分隔符 / 绝对路径。Rust `Path::join` 遇到绝对路径会丢弃前缀，`../` 会跳出 Downloads。同文件 `save_media_file` 用 `reject_unsafe_write_path`（:83-106），但该校验只把目标 parent 限制在 Downloads / Pictures / Videos / Desktop / Documents **任一**目录内——对 `save_text_file` 直接复用**并不足够**：`file_name = "../Documents/foo.txt"` 经 join + canonicalize 后 parent 落到 `~/Documents`（允许目录），仍会通过校验。
- **现象**：恶意或有缺陷的前端可让桌面端把导出内容（HAR / session / 规则等文本）写到 Downloads 之外（含 Documents / Desktop 等允许目录，或借绝对路径 / 多层 `../` 落到允许根目录内的任意位置）。
- **影响**：潜在的越界文件写入。当前前端调用方可控，但 Tauri 命令层是安全边界，应防御性校验。
- **修复方向**：`save_text_file` 的威胁模型是「前端只提供 basename，后端拼 Downloads」，应**先校验 `file_name` 是纯 basename**——拒绝含 `/` / `\` / `..` / `.`、以这些为前缀、或为绝对路径的输入——再拼到 `downloads_dir` 下。`reject_unsafe_write_path` 面向的是 `save_media_file`「前端传完整 path」的模型，不适用于此场景。

## 5. 🟠 高危（核心功能失效 / 资源耗尽 / 数据丢失）

### H1 ✅ 已修复（39eee5b） 节流规则草稿被 effect 立即回滚，规则字段无法编辑

- **位置**：`apps/desktop/src/features/throttling/use-throttle-editor.ts:187-197`
- **类别**：React 副作用缺陷 / 核心功能失效
- **确认依据**：
  ```ts
  useEffect(() => {
    if (selectedRule) {
      setRuleDraft(selectedRule);   // 无条件用 selectedRule 覆盖草稿
      return;
    }
    if (!ruleDraft && rules[0]) { ... }
  }, [ruleDraft, rules, selectedRule]);  // ruleDraft 在依赖数组中
  ```
- **现象**：依赖数组含 `ruleDraft`。用户在 RuleEditor 改任一字段 → `updateRuleDraft` → `setRuleDraft` → 本 effect 重跑 → 因 `selectedRule` 非 null，执行 `setRuleDraft(selectedRule)`，用未编辑的服务端值覆盖草稿。
- **影响**：节流规则编辑器实质不可用，用户改任何字段都会被立即还原。
- **修复方向**：仅在 `selectedRuleId` 真正变化时同步草稿（用 ref 记录上一次 id，id 变化时才 `setRuleDraft`），或引入 dirty guard（草稿有未保存编辑时不被服务端值覆盖）。**仅去掉 `ruleDraft` 依赖不够**——`rules` 来自 TanStack Query，任何 invalidate / refetch 都会产生新数组引用，`selectedRule`（`rules.find`）随之变引用，仍会触发 effect 覆盖正在编辑的草稿。H2 的 profile 草稿（依赖 `[mode, selectedProfile]`）属同一类「引用刷新覆盖」问题，需一并改为按 id 变化同步。

### H2 ✅ 已修复（39eee5b） 节流 Profile 草稿被引用变化覆盖 + 复制规则完全失效（与 H1 同源）

- **位置**：`apps/desktop/src/features/throttling/use-throttle-editor.ts:179-185`（profile 草稿）；`apps/desktop/src/features/throttling/components/RuleEditor.tsx:154-156`（复制规则）
- **类别**：React 副作用缺陷 / 数据丢失 / 功能失效
- **确认依据**：
  - profile 路径：`useEffect(..., [mode, selectedProfile])`，`mode === "profiles"` 时 `setProfileDraft(selectedProfile)`。保存或其它 mutation 使 query 失效重取，产生新的 `selectedProfile` 引用即触发覆盖。
  - 复制规则：`onChange({ id: crypto.randomUUID(), name: ... })` 只改了 `draft.id`，未同步 `selectedRuleId`。
- **现象**：profile 草稿在保存后被服务端值静默覆盖，丢失用户输入；复制规则后 `selectedRuleId` 仍指向原规则，触发 H1 的 effect 立刻把 draft 还原成原规则，复制结果瞬间消失。
- **影响**：节流 Profile 编辑与规则复制两条功能链均失效。
- **修复方向**：profile 草稿仅在 `selectedProfileId` 变化时同步，不在引用每次变化时覆盖；复制动作提升到 hook 层提供 `duplicateRule`，复制时同时 `setSelectedRuleId(newId)`。

### H3 ✅ 已修复（434945f） `send_direct_request` 无超时，挂起上游永久阻塞 Tauri 命令

- **位置**：`crates/proxy-core/src/server.rs:590-657`（`send_direct_request`）；client 构建在 `direct_http_client()`（:22-38）
- **类别**：超时缺失 / 资源占用
- **确认依据**：`direct_http_client()` 用 `Client::builder().redirect(Policy::none()).no_proxy().build()` 构建，**无 `connect_timeout` / `timeout` / `pool_idle_timeout`**。`request_builder.send().await`（:643-646）与 `read_response_body_with_limit`（:653-656）也无 `tokio::time::timeout` 包裹。
- **现象**：`send_direct_request` 被 Tauri 命令 `apps/desktop/src-tauri/src/commands/compose.rs:19` 直接 `await`。上游 TCP 连上但不回响应（或 body 极慢）时，该命令无限期挂起，UI 的「重发 / Compose」请求永远 pending，且 Tauri future 无法被取消。
- **影响**：与主代理路径（`http_proxy.rs:635` 有 `upstream_request_timeout` 包裹）行为严重不一致；用户用 Compose 重发到慢/挂起上游时功能卡死。
- **修复方向**：client builder 加 `.connect_timeout(...)`，`send` 与 body 读取套 `tokio::time::timeout(upstream_request_timeout(), ...)`，或在 client 上设 `.timeout(...)`。

### H4 ✅ 已修复（eff6fa1，idle-reset） CONNECT 盲隧道 connect / relay 无超时，可耗尽连接配额

- **位置**：`crates/proxy-core/src/connect.rs:35-52`（`tunnel_blind_relay`）
- **类别**：超时缺失 / 资源耗尽
- **确认依据**：`TcpStream::connect((&*connect_host, port)).await`（:35）无 connect 超时；`copy_bidirectional`（:49-52）无读/写空闲超时。该函数持有 `server.rs:148` 的 semaphore permit（上限 `MAX_CONCURRENT_CONNECTIONS=1024`）。
- **现象**：上游连得上但隧道建立后双方不发数据（或上游 TCP 不响应 connect）时，task 永久挂起，持续占用 permit。大量慢速 CONNECT 目标即可耗尽 1024 配额，导致代理拒绝所有新连接（`server.rs:131` 的 `max_connections_reached`）。
- **影响**：DoS 级资源耗尽。注：`copy_bidirectional` 的半关闭语义本身正确（前序审计 H6 已修复），缺超时是独立问题。
- **修复方向**：connect 用 `tokio::time::timeout(Duration::from_secs(N), TcpStream::connect(...))`；relay 外层套整体/空闲 deadline。

### H5 ✅ 已修复（5e7b966） h1 上游 conn driver 裸 spawn 丢句柄，超时后连接 / task 泄漏

- **位置**：`crates/proxy-core/src/upstream.rs:180-182`（h1 分支）；h2 pool 同模式见 `upstream_pool.rs:206-208`
- **类别**：task / 连接泄漏
- **确认依据**：h1 路径每次请求 `hyper::client::conn::http1::handshake` 后 `tokio::spawn(async move { let _ = conn.await; })`，JoinHandle 被丢弃。请求超时（`http_proxy.rs:635` 的 `upstream_request_timeout`）触发时 `forward_request` future 被 drop，但 spawn 出来的 conn driver **不会被 cancel**，继续持有 socket 直到对端 FIN。
- **现象**：高频超时场景下，每个被超时的请求留下一对半开 TCP + 一个永久 task，缓慢耗尽 fd / 内存 / 端口。h2 pool（`upstream_pool.rs:206-208`）同模式裸 spawn，但有 pool evict + `is_closed()` 检测，问题较轻。
- **影响**：长期运行下代理逐渐变慢直至资源耗尽。
- **修复方向**：保留 conn driver 的 JoinHandle，在 `send_request` 失败/超时后显式 abort；或 h1 路径也统一改用连接池（h2 已用 `upstream_pool`，h1 却是裸 spawn，两者不一致）。
- **实际修复（5e7b966，防御性加固）**：实测在当前 hyper 1.10.1 上，`SendRequest` drop 会关闭 dispatch channel → conn driver 自然终止（`natural_completions=1`），**原泄漏不可复现**。本次仍加了 RAII drop guard（成功路径 `disarm`，超时/提前 drop 时 abort）作为确定性兜底 + 前瞻性回归测试。h2 pool 因按连接池化 + `is_closed()`/evict 管理，未改。

### H6 ✅ 已修复（4981887） 断点 await 无超时 + pending map 泄漏

- **位置**：`crates/proxy-core/src/breakpoints.rs:534-550`（request stage）、`:591-604`（response stage）
- **类别**：超时缺失 / 状态泄漏 / 资源占用
- **确认依据**：`receiver.await`（oneshot）无任何超时包裹。`cancel_all()` 只在「代理停止」时调用（注释自述「this should no longer happen because cancel_all() sends a Forward resolution」，但 `cancel_all()` 仅 server 关闭路径触发）。`register_pending` 把 `(session_id, PendingBreakpoint{sender})` 插入 `pending` map，`receiver.await` 返回 `Err(_)` 分支只打 warn 日志返回 `Ok(None)`，**未从 pending map 移除**。
- **现象**：前端关闭 DevTools 窗口 / 刷新页面 / `emit_breakpoint_event`（fire-and-forget）投递失败或丢失时，前端永不回 `resolve`，对应代理连接 task 永久挂起，占用 upstream 连接与 pending map 条目。`Err` 路径不清理 map，map 持续膨胀。
- **影响**：单条请求级永久阻塞 + 内存泄漏。注：前序审计 H5 修复的是「Forward 丢失用户修改」，本条是独立的超时/泄漏问题。
- **修复方向**：`tokio::time::timeout`（可配置，如 5 分钟）兜底，超时后按 Forward 放行；`Err(_)` 分支主动 `bp.pending.lock().remove(&session_id)`，保持 map 与 receiver 生命周期一致。

### H7 ✅ 已修复（bc5ad78） `delete_sessions_by_ids` 大批量 ID 触发 SQLite 变量上限

- **位置**：`crates/db/src/sessions.rs:294-380`
- **类别**：数据库限制 / 静默失败
- **确认依据**：函数为整个 ID 列表构造一组 `?1..?N` 占位符并在多条 DELETE 中复用。SQLite 默认单语句变量上限 `SQLITE_LIMIT_VARIABLE_NUMBER`（旧版 999 / 新版 32766）。`ids.len()` 超限即 `prepare` 报错、整个删除事务回滚。调用方 `bootstrap/mod.rs:273` 在后台自动清理中批量传入待清理旧 session ID，失败被 `repository.rs:82` 的 `eprintln!` 静默吞掉。
- **现象**：session 积累到一定规模后，单次后台清理失败，旧 session 永远删不掉、DB 持续膨胀，且无用户/日志侧反馈。
- **影响**：长期使用下数据库膨胀不可控。
- **修复方向**：分批处理（如每批 ≤500 个 ID），或改用临时表 JOIN 删除。

### H8 ✅ 已修复（77d7e00） 切换环境丢失上一环境未保存的变量编辑（数据丢失）

### H9 ✅ 已修复（adbd8a6） WebSocket 中继：Close 后单向停止 + 退出条件需双端 Close

- **位置**：`crates/proxy-core/src/ws.rs:484-498`（client→upstream）、`:512-526`（upstream→client）、退出条件 `:558`
- **类别**：WebSocket 协议正确性 / 连接泄漏
- **确认依据**：一端发送 Close 帧时，代码先 `forward_raw_frame` 转发 Close 给对端，再把自己一侧标记 `client_done = true`，但**未主动关闭对侧写入，也未在对端方向 break 循环**。`loop` 退出条件是 `client_done && upstream_done`（:558），即必须两端都各自发 Close 才退出。
- **现象**：RFC 6455 §5.5.1 要求收到 Close 必须回 Close。这里转发 Close 后，若对端不回（实现不规范的 server / 网络丢包 / 对端已半关闭），这一侧 task 永远卡在 `parse_ws_frame`，TCP 连接泄漏。
- **影响**：WS 抓包场景下偶发的连接泄漏与挂起。
- **修复方向**：一端收到/转发 Close 后主动 shutdown 对端写入，并给 relay 加总超时（如收到 Close 后 30s 强制退出）；或退出条件改为「任一端 done 即关闭双方」。

### H10 ✅ 已修复（e10a3d6） WS 帧解析错误被静默当 EOF，不回 Close(1002)

- **位置**：`crates/proxy-core/src/ws.rs:477`、`:505`
- **类别**：WebSocket 协议正确性 / 可观测性
- **确认依据**：`parse_ws_frame(...).await.ok()` 把所有 `ProxyError`（含 reserved opcode / 控制帧分片 / payload 超 16MB / 读超时）一律转成 `None` → `done = true` → 静默结束。`parse_ws_frame` 内部已为协议违规生成 close-code 1002 语义，但 relay 既不回 Close 帧也不区分「正常 EOF」与「协议错误」。

### M4 ✅ 已修复（1ebfa77） CONNECT 盲隧道先发 200 再连上游，上游不可达时客户端拿到「假隧道」

- **确认依据**：第 18-21 行无条件先写 `HTTP/1.1 200 Connection Established`，**之后**（:35）才 `TcpStream::connect` 上游，失败 `map_err` 返回 Err。

## 8. ❓ 待实测确认

### N1 ❓ Windows 证书信任检查的 PowerShell param 绑定，怀疑恒返回「已信任」

- **位置**：`crates/tls-manager/src/trust.rs:60-106`（`is_trusted_windows` 脚本）
- **怀疑点**：脚本为 `r#"\nparam([string]$Thumbprint)\n..."#`，第一行是空行；调用为 `powershell -NoProfile -NonInteractive -Command <script> <thumbprint>`。怀疑 `param` 绑定失败 → `$Thumbprint=$null` → `$normalized` 为空串 → `Test-Path Cert:\CurrentUser\Root\`（容器路径）恒 true → 永远输出 `'True'`，UI 永远显示已信任。
- **不确定性**：PowerShell 允许 `param` 前有空行 / 注释，前导空行本身通常**不**破坏绑定；`-Command` 模式下的位置参数绑定也应有正常路径。需在真实 Windows 上复现验证。
- **建议**：在真实 Windows 上用合法 / 非法 thumbprint 各跑一次脚本，确认 stdout 输出。若绑定失败，把 `param(...)` 移到脚本绝对第一行（无前导空行）或改用 `-File` + `-ArgumentList`。

### N2 ❓ Linux 证书信任检测对 `ca-certificates.crt` 合并 bundle 漏检

- **位置**：`crates/tls-manager/src/trust.rs:167-257`（`is_trusted_linux`）
- **怀疑点**：`/etc/ssl/certs/` 下既有 subject-hash 单文件（`a1b2c3d4.0`），也有合并 bundle `ca-certificates.crt`。代码逐文件读 PEM、`lines().filter(!starts_with("-----"))` 拼接后 decode 算 SHA-1 指纹。对 bundle（多张证书）会把多张证书字节流拼接算一个「假指纹」，永远匹配不上真实证书。
- **后果**：Debian 系默认安装到 bundle 的发行版上，UI 永远显示未信任（false-negative 显示，非安全漏洞）。
- **建议**：按 `-----END CERTIFICATE-----` 切分 bundle，逐张算指纹比对（或用 `x509-parser`）。需在 Debian/Ubuntu 实测确认漏检。
