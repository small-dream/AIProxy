## 2. 结论先行

当前 Agent Access 的核心问题不是“开关数量多”，而是把**未来所有任务的安全决策**一次性压给用户。用户还不知道 Agent 要做什么，就被要求理解 17 个权限字段、12 个控制开关、自动化根目录、origin 白名单和高级脱敏策略。最终常见结果是：

1. 用户为了不被打断，直接打开“完整控制”。
2. 用户看不懂预留能力，误以为开关无效。
3. 用户被某个权限卡住后放弃 Agent 工作流。
4. 用户长期保留已经不需要的高风险权限。

本方案把 Agent Access 从“权限配置矩阵”调整为“**能力授权中心**”，分三层交付：

- **L1 简单模式**：用户先选择任务场景，不需要理解字段名。
- **L2 限时授权**：Agent 在具体动作发生时请求权限，用户按动作、范围、时长批准。
- **L3 高级模式**：需要精细控制的用户才展开完整权限矩阵。

实施上不推倒现有后端权限模型。P0-A 只重构信息架构和文案；P0-B 再补充场景预设与立即收回控制；P1 在现有布尔权限之上增加限时授权（lease）；P2 再扩展按 workspace、按项目和使用洞察的长期策略。

一句话产品原则：

> 不要让用户预判未来，让用户在具体动作发生时做一次知情决定。

评审结论（已落实）：

> 方向认可。P0-A 先交付确定性的信息架构改进；P0-B 在修订依赖与全局影响后交付场景预设、立即收回控制；P1 在补齐实例身份、动作指纹、非幂等未知结果、审批恢复流程和资源生命周期后交付首版限时授权。三者现已实现，后续变化以 `ADR-011`、`API_SPEC.md`、`ARCHITECTURE.md` 和页面规范为准。

## 3. 背景与问题定义

### 3.1 当前页面结构

当前 Settings > Agent Access 主要由以下区块组成：

1. 启用开关、服务状态和版本。
2. 客户端连接列表。
3. 读取权限：会话元数据、响应 Body、WebSocket。
4. 控制权限：抓包与工作区、系统代理、根证书、删除会话、重放、临时规则、Agent 自动化、我的自动化、脚本、跨 host 映射、代理验证、全局自动化。
5. 自动化资源边界：Map Local 根目录、代理验证 origin、跨 host 映射 origin。
6. 高级权限：未脱敏 Body、格式识别、标识符哈希、自定义敏感字段、最大会话数、Body 分块上限。
7. 审计日志和保存操作。

当前实现与设计约束见 `docs/PAGE_BLUEPRINTS.md`、`docs/UI_GUIDELINES.md` 和 `apps/desktop/src/pages/settings/sections/AgentAccessSection.tsx`。

### 3.2 根因：静态权限与任务意图错位

权限本身没有错，错在授权时机和表达方式：

- 用户在“还不知道要做什么”时配置“Agent 未来能做什么”。
- 权限是全局长期的，但页面文案要求“只开启当前任务需要的权限”。
- 用户无法从 `Manage Agent automation` 这样的字段名推断实际后果。
- 高风险和低风险权限使用同一种开关控件和相近视觉权重。
- 未开放能力与已开放能力混在一起，用户无法判断哪些开关真正生效。
- Agent 需要权限时只能失败，不能把“我需要什么、为什么需要、影响范围多大”告诉用户。

### 3.3 具体问题清单

| 优先级 | 问题 | 用户影响 | 本方案处理 |
|---|---|---|---|
| P0 | 12 个控制权限平铺 | 阅读负担高，无法快速判断风险 | 按用户结果分 4 组，默认只展示场景模式 |
| P0 | “启用完整控制”过于显眼 | 容易一键过度授权 | 降级到更多菜单，并要求高风险确认 |
| P0 | 脚本、跨 host、全局自动化尚未开放却显示开关 | 用户误以为配置后可用 | 从主权限矩阵移除，只在“尚未开放”说明中出现 |
| P0 | 自动化边界在未启用自动化时也展示 | 用户不知道为什么要配置 | 仅在自动化能力被选中时显示 |
| P0 | 缺少当前能力摘要 | 用户无法确认 Agent 现在能做什么 | 首屏提供一句话能力摘要和风险状态 |
| P0 | 保存入口在页面底部 | 改动多时容易漏保存或忘记改了什么 | 固定保存栏 + 变更摘要 + 高风险确认 |
| P1 | 只能长期预授权 | 用户被迫过度授权或频繁进设置 | Agent 请求时按动作、范围、时长批准 |
| P1 | 权限范围不可收窄 | 读取 Body、自动化实验都是全局级别 | 增加 session/host/root/origin 等 lease 范围 |
| P1 | 授权后缺少反馈和回收入口 | 用户不知道 Agent 用了什么、何时失效 | 待授权、最近授权、到期时间、立即撤销 |

### 3.4 评审核实记录

本轮评审中的关键判断已对照现有代码和规范核实：

| 评审点 | 核实结果 | 对方案的影响 |
|---|---|---|
| 代理验证与自动化的权限依赖 | `ControlOperation::VerifyAutomationChange` 始终要求 `manageAutomation`；`mode=proxy` 时再要求 `manageProxiedVerification`。因此只开 `manageProxiedVerification` 无法完成代理验证。 | 删除“调试与验证”预设；代理验证只放入自动化能力组合，并明确依赖 `manageAutomation`。 |
| 是否存在连接实例或任务标识 | Sidecar 当前只通过 MCP `clientInfo` 获得客户端名称和版本，没有会话 ID、对话 ID 或任务 ID；`AppContext` 也没有实例标识。 | 不承诺“任务结束自动失效”；改为“限时授权”，并要求新增 sidecar 实例 ID。 |
| 重放能否绑定具体操作 | `ReplaySessionParams` 已包含 `sessionId`、方法、Header/Query 覆盖、Body 和 JSON 修改，能够生成稳定的操作指纹；但当前审批模型没有指纹。 | 重放授权必须绑定具体请求指纹；非幂等请求只允许一次。 |
| 授权到期是否等于资源停止 | 自动化资源有独立的 `persistent` / `ephemeral` 生命周期和 `ttlSeconds`（60–3600 秒）；权限撤销不会自动回滚或停止已创建资源。 | 必须分别定义授权有效期、实验有效期和资源清理；撤销时要展示仍在生效的资源。 |
| 是否已有两套权限模型 | 现有配置是全局布尔权限；连接对话框已有权限模板。新增 `grantRequestPolicy` 会形成第二套状态。 | UI 统一为“禁止 / 请求时询问 / 始终允许”三态，后端保留兼容字段；连接对话框与设置页共用同一套预设。 |
| 系统代理、抓包和证书是否随权限失效 | 这些操作产生的是独立运行时状态或系统状态，权限只是调用门槛；撤销权限不会自动停止抓包、恢复系统代理或撤销证书信任。 | 收回控制必须展示副作用并提供停止抓包、恢复系统代理、移除证书信任等收尾动作。 |

## 4. 产品目标与原则

### 4.1 目标

1. 提高 Agent 任务完成率，而不是单纯缩短设置页停留时间。
2. 降低每个成功任务的人工打断次数；需要授权时只打断一次，批准后原调用继续。
3. 提高审批后的恢复成功率，避免用户批准后仍要在聊天里重复一次“我批准了”。
4. 默认配置保持最小权限，不因升级自动扩大任何控制权限。
5. 高风险操作有明确动作预览、范围、时长和撤销入口。
6. 撤销权限后，所有仍在生效的资源、抓包状态、系统代理和证书信任都可见并可收尾。
7. 高级用户仍可精确控制每一项权限，不牺牲专业能力。

### 4.2 产品原则

- **默认最小**：首次连接只授予完成只读分析所需的最小范围。
- **限时授权优先**：权限围绕动作而不是字段名；在无法可靠识别任务边界前，只承诺按时间、次数和操作指纹失效，不承诺“任务结束自动失效”。
- **先解释再授权**：授权前展示动作、目标、影响和风险，不用实现术语。
- **不可静默升权**：任何新权限、范围扩大或高风险操作都必须有可见确认。
- **可撤销、可审计**：用户随时能收回权限，并能看到最近授权和 Agent 使用记录。
- **渐进披露**：首屏只回答“你现在想做什么”，高级矩阵放在第二层。
- **保留逃生通道**：Agent 因权限不足失败时，必须给出可执行的“去授权”路径，而不是只说 `PERMISSION_DENIED`。

### 4.3 非目标

- P0/P1 不引入账号、云端权限同步或团队 RBAC。
- 不开放 Agent 修改自身权限、MCP 配置或 Skill。
- 不把权限变更做成静默生效；静态权限仍需要保存。
- 不为了简化而删除高风险权限，只调整呈现和授权方式。
- 不在本方案中改变现有工具契约、审计字段和权限字段语义。
- 在客户端未提供会话/任务标识前，不承诺“任务结束”能自动识别或自动撤销授权。
- 不把权限撤销伪装成资源清理；权限撤销与运行时副作用收尾必须分开表达。

## 5. 目标体验

### 5.1 用户旅程

```text
连接 Agent
  → 选择权限预设（仅元数据 / 只读分析（推荐）/ 调试与重放 / 自动化实验）
  → Agent 开始工作
  → 缺少权限时弹出限时授权卡
  → 用户允许一次或允许 15 分钟
  → 批准后原调用继续；授权按到期时间失效
  → 资源与运行时副作用按各自生命周期单独收尾
  → 设置页保留最近授权和审计记录
```

### 5.2 两个关键界面

**设置页**回答“Agent 长期可以做什么”。

**限时授权卡**回答“Agent 现在想做什么，是否允许”。

两者不能混成一个页面。设置页不再要求用户提前理解所有未来动作，授权卡也不替代长期策略。

## 6. 信息架构重构

### 6.1 首屏结构

首屏按“是否已有客户端”分两种布局，避免首次连接和权限管理互相干扰：

**尚无客户端时**

1. 启用开关和一句数据流向说明。
2. 客户端连接引导（Codex / Claude Code / Cursor）。
3. 连接对话框内选择权限预设。
4. 高级权限默认折叠，不作为首次路径。

**已有客户端时**

1. **能力摘要卡**
   - 展示**当前已生效**权限，不展示草稿。
   - Agent 当前可以：读取会话元数据、读取脱敏 Body。
   - Agent 当前不可以：控制抓包、删除会话、修改自动化。
   - 当前预设：只读分析（推荐）；无法精确匹配时显示“自定义”。
   - 操作：`调整权限`、`立即收回控制`。
2. **权限预设**
   - 下拉框，默认只做精确匹配；匹配不到就是“自定义”，不使用“最接近模式”掩盖差异。
   - 每个预设显示一句结果描述、包含的能力和风险等级。
3. **待授权**
   - 仅在存在 pending 请求时出现。
   - 显示 Agent 客户端、动作、目标、范围和剩余时间。
4. **最近授权**
   - 显示未过期的限时授权、到期时间和 `撤销`。
5. **客户端连接**
   - 保留现有紧凑列表；连接对话框与设置页共用同一套预设定义。
6. **高级权限**
   - 默认折叠，包含完整权限矩阵、脱敏策略和限制。
7. **审计**
   - 保留现有摘要和表格。

权限是全局配置：在连接另一个客户端时调整模板，会影响所有已连接客户端。连接对话框必须明确提示这一点，不能把模板描述成“只对当前客户端生效”。

### 6.2 权限预设

P0-B 提供 4 个可解释的权限预设；“完全控制”不再作为独立预设，改为高级区里的批量授权操作：

| 预设 | 面向场景 | 默认包含 | 默认排除 | 风险提示 |
|---|---|---|---|---|
| 仅元数据 | 只想看请求、状态码、Timing | `readSessions` | Body、WebSocket、全部控制 | 最低 |
| 只读分析（推荐） | 需要分析响应字段和错误；新配置默认值 | `readSessions`、`readBodies`、默认脱敏 | 未脱敏 Body、WebSocket、全部控制 | 低 |
| 调试与重放 | 需要向真实上游重放请求 | 只读分析 + `sendRequests` | 自动化、系统代理、证书、删除 | 中 |
| 自动化实验 | 需要创建、验证、回滚 Agent 自有 Rewrite / Map Local 资源 | 只读分析 + `manageAutomation` | 用户资源修改、全局自动化、脚本、跨 host、抓包控制 | 中高 |

预设内可以再提供按功能开启的子选项，而不是把所有依赖一次性打开：

- `允许代理主动验证`：在自动化实验预设下追加 `manageProxiedVerification`，并要求配置验证 origin。
- `使用 Map Local`：要求配置至少一个批准根目录；只做 Rewrite、离线验证或真实客户端验证时不需要根目录。
- `读取 WebSocket`：独立读取选项，不随“调试”或“自动化”自动开启。
- `允许抓包控制`：独立操作能力，不随自动化实验自动开启。

新配置默认 `只读分析（推荐）`，仍保持未脱敏 Body、WebSocket、导出和控制权限关闭。老用户只有与某个预设完全一致时才显示该预设，否则显示 `自定义`，不自动改写权限。

预设只是草稿快捷方式，仍然需要点击保存。预设不得用无关授权来换取“少点几次”。

### 6.3 权限预设与现有权限字段映射

下表是 P0-B 的初始映射，实施时需要由纯函数生成并可单测：

| 权限字段 | 仅元数据 | 只读分析（推荐） | 调试与重放 | 自动化实验 | 说明 |
|---|---:|---:|---:|---:|---|
| `readSessions` | 开 | 开 | 开 | 开 | 所有模式的基础读取 |
| `readBodies` | 关 | 开 | 开 | 开 | 默认脱敏 |
| `readWebSocket` | 关 | 关 | 关 | 关 | 需单独开启 |
| `readRawBodies` | 关 | 关 | 关 | 关 | 始终独立高风险项 |
| `controlCapture` | 关 | 关 | 关 | 关 | 需单独开启 |
| `controlSystemProxy` | 关 | 关 | 关 | 关 | 只允许高级设置或显式任务批准 |
| `manageCertificates` | 关 | 关 | 关 | 关 | 只允许高级设置或显式任务批准 |
| `deleteSessions` | 关 | 关 | 关 | 关 | 不随任何预设开启 |
| `sendRequests` | 关 | 关 | 开 | 关 | 非幂等重放仍需一次一授权 |
| `manageRules` | 关 | 关 | 关 | 关 | 临时规则是独立能力，不随自动化预设开启 |
| `manageAutomation` | 关 | 关 | 关 | 开 | 所有自动化工具的基础权限 |
| `manageUserAutomation` | 关 | 关 | 关 | 关 | 不随预设开启 |
| `manageScripts` | 关 | 关 | 关 | 关 | 当前不可用 |
| `manageCrossHostMappings` | 关 | 关 | 关 | 关 | 当前不可用 |
| `manageProxiedVerification` | 关 | 关 | 关 | 关（可选） | 选择“代理主动验证”时追加 |
| `manageGlobalAutomation` | 关 | 关 | 关 | 关 | 当前不可用 |

说明：

- `verify_automation_change` 始终要求 `manageAutomation`；只有 `mode=proxy` 才额外要求 `manageProxiedVerification`。因此“调试与重放”不能承诺代理验证。
- Map Local 根目录只在创建/读取 Map Local 资源时需要；代理验证 origin 只在 `mode=proxy` 时需要。Rewrite、离线验证和真实客户端验证不应被这两项阻断。
- 高级区可以提供“勾选全部当前可用控制”批量操作，但必须展示字段级 diff 和高风险确认，不能命名为“完全控制”或“一键安全”。

### 6.4 权限分组

自定义模式中，按用户结果分组，而不是按 MCP 字段顺序：

1. **读取数据**
   - 会话元数据
   - 响应 Body
   - WebSocket 消息
   - 未脱敏 Body（高风险，默认折叠）
2. **控制桌面**
   - 抓包与工作区
   - 系统代理
   - 根证书
3. **修改请求**
   - 重放请求
   - 临时规则
   - 代理验证
4. **Agent 自动化**
   - 创建/验证/回滚 Agent 自有资源
   - 修改用户资源（高风险）
   - 自动化根目录与 origin（按需显示）
5. **危险操作**
   - 删除会话
   - 清空会话
   - 撤销证书信任
   - 修改用户资源

每组标题右侧展示风险 Chip，例如 `读取`、`会影响流量`、`不可恢复`。组内每项使用“用户结果 + 一句示例”，例如：

> 重放请求  
> 让 Agent 向原始 host 重新发送一条已捕获请求。重放不经过 AIProxy 规则，可能产生真实副作用。

### 6.5 自动化资源边界

自动化边界按“具体功能”出现，而不是按“自动化总开关”强制要求：

- 未启用 `manageAutomation`：显示一行说明和 `启用后配置`，不显示输入框和列表。
- 启用 `manageAutomation` 但未使用 Map Local：不要求根目录；列表以折叠状态展示。
- 使用 Map Local：要求至少一个批准根目录，并在保存/创建资源前提示缺失。
- 选择代理主动验证：要求至少一个精确 origin，并追加 `manageProxiedVerification`。
- 只做 Rewrite、离线验证或真实客户端验证：不要求根目录或 origin。
- 跨 host 映射当前不可写：显示为只读说明，不提供 `Add` 输入框。
- 根目录和 origin 的添加动作应支持从授权卡直接发起，避免用户先去设置页再回来重试。

### 6.6 高级设置

高级区默认折叠，包含：

- 未脱敏 Body。
- 格式识别、标识符哈希、自定义敏感字段。
- 最大会话数、Body 分块上限。
- 权限矩阵。

高级区顶部显示：

> 这些设置面向需要精确定义读取范围和脱敏策略的用户。普通排查通常不需要修改。

### 6.7 保存与变更审阅

建议改为固定底部操作栏：

```text
本次将新增 3 项权限，其中 1 项会修改系统代理  [查看变更] [保存] [放弃]
```

规则：

- 任何权限变更都先进入草稿。
- 有变更时固定栏出现，显示变更数量和风险摘要。
- 摘要区始终同时展示“当前生效”和“待保存”；草稿不得伪装成已生效权限。
- 点击 `查看变更` 展示字段级前后对比。
- 包含删除、系统代理、证书信任、修改用户资源时，必须二次确认。
- 保存成功后显示“已保存，正在运行的 Agent 会在下一次工具调用时使用新权限”。
- 页面离开前有未保存变更时提示确认。

例外：`立即收回控制` 不进入草稿，直接写入并立即生效。它与普通编辑使用不同的 API 和确认文案，避免用户误以为权力已经收回。

### 6.8 立即收回控制

首屏和能力摘要卡提供 `立即收回控制`：

- 立即生效，不进入草稿。
- 保留读取权限，关闭全部控制与自动化权限，同时清除所有临时授权。
- 二次确认，明确说明：**停止授权不等于停止已经发生的副作用**。
- 操作前展示当前仍在生效的对象：
  - 正在抓包的 workspace；
  - AIProxy 接管的系统代理；
  - 已安装/信任的根证书；
  - Agent 创建的临时规则、持久规则和自动化资源；
  - 仍可被 Agent 读取的会话/日志范围。
- 提供对应收尾入口：停止抓包、恢复系统代理、撤销证书信任、清理临时资源、回滚或清理自动化资源。
- 操作后展示“已收回的权限”“仍保留的读取范围”“仍在生效但需要手动处理的资源”。

权限撤销和实验清理是两个独立动作。默认不应把撤销权限自动扩大为删除用户资源；但必须让残留资源可见、可处理，并允许用户选择“收回并清理 Agent 自有资源”。

## 7. 限时授权（P1，首版已实现）

> 首版已按 `docs/DECISIONS/ADR-011-agent-access-limited-grants.md` 实现：绑定 sidecar 实例、客户端、能力与动作指纹；审批等待 30 秒、拒绝冷却 60 秒；一次性授权 60 秒内 1 次，可重复授权 15 分钟内最多 50 次；非幂等与高风险动作只允许一次；授权到期与资源生命周期分别处理。

### 7.1 核心模型

保留现有静态布尔权限作为“长期允许”，新增独立的“是否允许 Agent 请求限时授权”策略，以及限时授权 lease：

```ts
type AgentAccessGrant = {
  id: string;
  requestId: string;
  clientName: string;
  clientVersion: string;
  agentInstanceId: string;
  client: "codex" | "claude" | "cursor";
  capability: AgentCapability;
  requestedScope: {
    sessionIds?: string[];
    connectionIds?: string[];
    host?: string;
    pathPrefix?: string;
    methods?: string[];
    workspaceId?: string;
    automationRoots?: string[];
    origins?: string[];
  };
  approvedScope: AgentAccessGrant["requestedScope"];
  actionFingerprint: string;
  reason: string;
  createdAt: string;
  approvedAt?: string;
  expiresAt: string;
  maxUses: number;
  remainingUses: number;
  resourcePolicy?: {
    lifecycle: "ephemeral" | "persistent";
    ttlSeconds?: number;
    cleanup: "agent_owned_only" | "manual";
  };
  status:
    | "pending"
    | "approved"
    | "executing"
    | "succeeded"
    | "failed"
    | "unknown"
    | "expired"
    | "revoked"
    | "denied"
    | "cancelled";
};
```

能力示例：

- `readBodies`
- `readRawBodies`
- `readWebSocket`
- `replaySession`
- `controlCapture`
- `manageAutomation`
- `manageProxiedVerification`

### 7.2 授权身份与任务边界

现有 MCP 连接只提供 `clientInfo.name` 和 `clientInfo.version`，没有对话 ID、任务 ID 或可跨工具调用复用的会话标识。首版因此使用 sidecar 进程内 `agentInstanceId` 缩小复用范围，但仍接受同一 sidecar 被多个对话共享：

1. Sidecar 在进程启动时生成随机 `agentInstanceId`，写入 grant store 并用于审批绑定。
2. 授权至少绑定 `agentInstanceId + clientName + clientVersion + capability + actionFingerprint`。
3. 如果同一个 Sidecar 进程被多个对话共享，这些对话仍会共享同一份限时授权；这是已知限制，必须写进文档。
4. 未来只有在客户端提供稳定 conversation/task ID 后，才能把授权进一步收窄到单个对话或任务。

在补齐上述身份前：

- 产品文案统一使用“限时授权”，不使用“任务完成后自动失效”。
- 不提供“开启直到任务结束”的选项。
- 应用退出时清除所有未完成/未过期的限时授权；重启后不恢复。

### 7.3 授权卡

Sidecar 在权限不足时返回结构化错误：

```json
{
  "code": "APPROVAL_REQUIRED",
  "requestId": "grant_01J...",
  "agentInstanceId": "mcp_01J...",
  "action": "replaySession",
  "summary": "重放 POST https://api.example.com/orders",
  "actionFingerprint": "sha256:...",
  "scope": {
    "sessionId": "sess_01J...",
    "host": "api.example.com",
    "pathPrefix": "/orders",
    "method": "POST"
  },
  "reason": "需要重新发送这条请求以对比服务端响应",
  "approvalOptions": ["once"],
  "expiresInSeconds": 60
}
```

桌面端展示授权卡：

> Codex 请求重放请求  
> `POST https://api.example.com/orders`  
> 请求指纹：`sha256:...`（批准只对当前方法、URL、Header、Query、Body 生效）  
> 原因：需要重新发送这条请求以对比服务端响应  
> 风险：会向真实上游发出请求，不经过 AIProxy 规则  
> [允许一次] [拒绝]

规则：

- 用户只能从桌面 UI 批准，Agent 不能自行批准。
- 默认选项是 `允许一次`，不是长期允许。
- 非幂等重放（`POST` / `PUT` / `PATCH` / `DELETE` 等）只提供 `允许一次`，不提供 15 分钟选项。
- 幂等只读请求（`GET` / `HEAD` / `OPTIONS`）和纯读取操作可以提供 15 分钟选项，但必须绑定 host、路径和时间窗口。
- 同一 `agentInstanceId + capability + actionFingerprint` 的重复请求合并为一个 pending，避免授权疲劳。
- 高风险操作（删除、修改用户资源、撤销证书信任、系统代理）只允许“允许一次”；永久允许必须在高级设置中单独开启。
- 如果用户批准后操作参数发生变化，指纹失效，必须重新审批。
- 审批卡显示的范围必须来自解析后的真实目标：重放先按 `sessionId` 读取会话摘要，再展示实际 host、path 和最终方法；会话不存在时返回 `SESSION_NOT_FOUND`，不创建审批卡。
- 一个动作缺少多个能力时，按缺失能力分别申请 grant；桌面端逐能力校验，不能因兄弟能力的 grant 而把整个动作判为不匹配。

### 7.4 读取权限的限时授权

读取工具不经过桌面控制通道时，sidecar 需要先检查本地 grant store：

1. 静态权限允许 → 直接读取。
2. 静态权限不允许，但存在匹配的 `approved` grant → 读取并扣减使用次数。
3. 都没有且 `grantRequestPolicy=ask` → 创建 pending 请求，通过审批通道通知桌面端，并在同一个工具调用内等待批准（默认最多 30 秒）。
4. 用户批准后，sidecar 继续原工具调用并返回真实结果；Agent 不需要回到聊天里再发一次“已批准”。
5. 拒绝、取消或超时返回结构化错误；不能把“最近一次授权”自动套用到新请求。

`readSessions` 是例外：它没有独立的 grant 消费链路，不提供 `grantRequestPolicy=ask`。用户需要读取会话元数据时必须直接设为“始终允许”，避免出现批准后仍无法读取的假入口。

审批通道要求：

- Sidecar 需要一条新的本地审批 IPC（可复用 owner-only control channel），不能只依赖静态配置文件轮询。
- 桌面端未运行时，只读工具返回 `APPROVAL_UNAVAILABLE` 和“打开 AIProxy 完成授权”，不自动启动应用。
- 写工具可以沿用现有自动拉起行为，但拉起后必须聚焦待授权项。
- 同一 Sidecar 实例同类请求同时只允许一个 pending；后续请求附加到同一个 pending，不重复弹卡。

范围必须收窄：

- Body 读取优先按 `sessionId` 授权。
- 批量读取按 `host + 时间窗口` 授权。
- 原始 Body 始终单独批准，不随普通 Body 授权继承。
- WebSocket 读取按连接 ID 或 host 授权。

### 7.5 重放与真实副作用

`replay_session` 会直接向原始上游发送真实请求，必须比普通读取更严格：

1. 授权绑定到具体执行计划，而不是只绑定 host 或客户端。
2. `actionFingerprint` 至少包含：原始 `sessionId`、最终方法、最终 URL（含 Query）、最终 Header 集合、最终 Body/JSON 覆盖结果的哈希。
3. 指纹中不保存明文 Header/Body，只保存规范化哈希和可审计的字段名。
4. 用户批准一次，只代表一次发送尝试；方法、URL、Header、Query、Body 任一变化都必须重新审批。
5. 如果请求在发送前失败（预检失败、证书错误、连接建立失败），可以判定为未产生副作用，不消耗授权；如果已经尝试发送但响应丢失，状态标记为 `unknown`，不得自动重试，必须由用户明确批准第二次尝试。
6. 非幂等方法只提供 `允许一次`。`GET` / `HEAD` / `OPTIONS` 可以在明确绑定 host、路径和时间窗口的前提下提供 15 分钟授权。
7. 继续使用现有单次重放闸门和频率限制；授权次数不能绕过并发限制。
8. 若工具调用在发送前被取消，授权作废，sidecar 不得在后台继续发送。

### 7.6 授权有效期与资源有效期

授权过期不代表动作效果结束。两者必须分别展示和收尾：

| 能力/动作 | 授权失效后会发生什么 | 仍需用户处理的效果 |
|---|---|---|
| 读取 Body / WebSocket | 后续读取被拒绝 | 已发送给模型服务商的内容无法撤回 |
| 重放请求 | 后续重放被拒绝 | 已发出的请求和上游副作用不会撤销 |
| 抓包控制 | Agent 不能再次启停 | 抓包可能仍在运行 |
| 系统代理 | Agent 不能再次切换 | 系统代理可能仍由 AIProxy 接管 |
| 根证书 | Agent 不能再次生成/移除信任 | 证书可能仍被系统信任 |
| 临时规则 | Agent 不能继续管理 | 规则可能仍在内存中生效，直到 TTL/重启/手动删除 |
| `ephemeral` 自动化资源 | Agent 不能继续管理 | 资源会在 `ttlSeconds`（60–3600 秒）到期或重启恢复时清理；可能仍有短暂残留 |
| `persistent` 自动化资源 | Agent 不能继续管理 | 资源持续生效，直到显式回滚或清理 |

产品规则：

- 限时授权必须同时展示 `expiresAt` 和“是否会清理资源”。
- 自动化限时授权默认只允许 `ephemeral`；申请 `persistent` 必须单独批准并明确“不会随授权到期自动回滚”。
- 授权撤销后，摘要页仍展示“仍在生效的资源”，并提供清理/回滚入口。
- 授权到期/撤销不得静默删除用户资源；只允许在用户明确选择时清理 Agent 自有资源。

### 7.7 授权生命周期

- 用户可选择“允许一次”（60 秒内 1 次）或“允许 15 分钟”（最多 50 次）；非幂等与高风险操作只提供“允许一次”。
- 授权次数不能绕过现有串行锁、重放限流、代理验证限流与资源 TTL。
- 无法可靠识别任务结束时，不承诺“任务结束自动失效”；应用退出时清除所有临时授权。
- 用户可随时撤销。
- 审计记录包含 `grantId`、批准方式、范围、使用次数和撤销时间。
- Agent 不能通过任何工具读取 grant store 路径或修改 grant。

### 7.8 与静态权限的关系

用户界面只表达三种状态，不再同时暴露“永久开关”和“可请求开关”两套矩阵：

| UI 状态 | 行为 | 后端映射 |
|---|---|---|
| 禁止 | 直接拒绝，不弹卡 | 静态权限 `false` + `grantRequestPolicy=deny` |
| 请求时询问 | 静态权限为开时不弹卡；为关时弹授权卡 | 静态权限按需 + `grantRequestPolicy=ask` |
| 始终允许 | 直接调用，不弹卡 | 静态权限 `true`，不依赖限时授权 |

规则：

- `始终允许` 和 `请求时询问` 互斥；用户不能看到“关闭但仍可永久调用”的矛盾状态。
- `readSessions` 只提供 `禁止 / 始终允许` 两态；后端会把旧配置中的 `ask` 归一化为 `deny`。
- 高风险能力（删除、系统代理、证书信任、修改用户资源）默认 `禁止`；开启 `请求时询问` 也必须进入高级设置，且授权卡只提供一次批准。
- 高风险能力的 `始终允许` 必须单独确认，不能通过预设或批量勾选静默开启。
- 限时授权只能授予 `请求时询问` 的能力，不能突破用户配置的根目录、origin、TTL 等范围上限。
- `立即收回控制` 同时把控制类能力置为 `禁止` 并清除所有限时授权，避免“看似关闭但 Agent 仍能弹卡”。

### 7.9 审批状态机与恢复

审批必须是一个闭环，而不是“返回错误，让 Agent 自己猜”：

```text
pending
  ├─ approve → approved → executing → succeeded
  │                              ├─ failed（未产生副作用）
  │                              └─ unknown（可能已发送）
  ├─ deny → denied
  ├─ timeout → expired
  └─ cancel → cancelled
```

规则：

- 待授权入口必须全局可达：AppShell 顶部提示或通知，不要求用户先进入 Settings。
- pending 请求在页面切换后仍然存在；设置页负责管理和历史，不是唯一入口。
- 用户批准后，桌面端通过审批通道唤醒等待中的 sidecar，原工具调用继续执行，不需要 Agent 回聊天重试。
- 拒绝返回 `APPROVAL_DENIED`，超时返回 `APPROVAL_TIMEOUT`，取消返回 `APPROVAL_CANCELLED`；Agent 不得自动循环重试。
- 同类请求在拒绝后有冷却时间（建议 60 秒），冷却期间重复请求直接拒绝，避免刷屏。
- `unknown` 必须显式标记，告知“可能已产生副作用”，并要求用户决定是否再次批准。
- 所有 pending、批准、拒绝、取消、超时、执行结果和撤销写入审计。

| 临时授权即将过期 | 显示剩余时间，不弹全局 toast |
| 临时授权已过期 | 从“最近授权”移除或折叠到历史，不改变静态权限 |
| 审批等待中 | 全局待授权入口显示动作、目标、指纹和剩余时间 |
| 审批拒绝 | 显示拒绝结果和冷却时间，不自动重试 |
| 审批超时 | 标记 `APPROVAL_TIMEOUT`，保留可重新发起入口 |
| 执行结果未知 | 标记“可能已产生副作用”，要求用户决定是否再次批准 |

### 8.3 文案规则

- 不出现 `manageUserAutomation`、`readRawBodies` 等字段名作为主标签。
- 每个权限必须包含“能做什么”和“可能造成什么影响”。
- 可请求临时授权的能力使用 `禁止`、`请求时询问`、`始终允许` 三态；`readSessions` 只使用 `禁止 / 始终允许`。授权卡使用 `允许一次`、`允许 15 分钟`（仅幂等读取/只读请求）、`拒绝`，不使用模糊的“确定”。
- 不把未开放能力写成“已预留可开启”。应写“当前版本不开放，开关不会绕过 `FEATURE_NOT_AVAILABLE`”或直接不展示。
- 高风险操作必须写明“不可恢复”或“会产生真实外部请求”。
- 不使用“完全控制”作为模式名；高级区使用“批量选择当前可用能力”，并展示逐项 diff。
- 不使用“任务结束自动失效”；统一写“限时授权会在到期、撤销或应用退出时失效”。

### 8.4 首次连接与全局作用域

首次连接和设置页必须共用同一套预设定义，避免两个入口语义不同：

1. 无客户端时，首屏先展示连接引导；连接对话框内选择模式，确认后保存权限并写入配置。
2. 已有客户端时，设置页的模式选择器与连接对话框使用同一组预设和风险说明。
3. 连接另一个客户端时，如果当前权限与预设不同，对话框默认选择 `保留当前权限`，不得静默重置。
4. 权限是全局配置：调整某个客户端的连接模板会影响所有已连接客户端，对话框和保存确认必须明确写出影响范围。
5. 首次安装所需的证书、抓包和系统代理属于独立操作能力，不能与删除会话、修改用户资源捆绑成“一键完整控制”。

## 9. 数据与接口影响

### 9.1 P0-A：不改后端协议

P0-A 只做前端信息架构和纯函数映射：

- 新增 `permissionPresets` 映射：权限字段 → 模式、分组、风险等级、依赖。
- 现有 `AgentAccessConfig`、Tauri command 和 MCP 工具契约不变。
- `get_agent_access_settings` / `update_agent_access_settings` 继续返回和保存完整布尔字段。
- 旧配置加载时只做精确匹配；无法精确匹配时显示“自定义”，不使用“最接近模式”推断，也不自动改字段。

### 9.2 P0-B：立即收回控制接口

P0-B 的普通预设选择仍只修改草稿；`立即收回控制` 需要独立 command，原因是它必须绕过草稿立即落盘，并返回当前运行时副作用：

- 新增 `revoke_agent_control_permissions`：一次性关闭控制与自动化权限、把控制类请求策略改为 `deny`、清除全部临时授权，保留读取权限，并返回 `revokedCapabilities`、`retainedReadCapabilities`、`activeEffects` 与 `grantsCleared`。
- 返回 `activeEffects`：正在抓包的 workspace、系统代理状态、证书信任状态、Agent 创建的临时/持久规则、自动化资源及其 workspace/scope。
- 不自动停止抓包、恢复系统代理、撤销证书信任或删除资源；这些动作分别调用现有控制命令，并且每项都需要明确确认。
- 桌面端在收回成功后立即刷新能力摘要和副作用清单，不能只提示“已关闭权限”。
- P1 已接入 grant store；该接口在同一次操作中清除全部临时授权。`grantsCleared=false` 表示权限已落盘但授权文件清理失败，UI 必须提示重启。

### 9.3 P1：新增 grant store 与审批通道

建议新增独立文件 `<data-dir>/agent-grants.json`，避免把临时授权混入长期 `agent-access.json`：

```ts
type GrantRequestPolicy = Record<AgentCapability, "ask" | "deny">;

type AgentGrantStore = {
  version: 1;
  grants: AgentAccessGrant[];
};
```

接口影响：

- `agent-access.json` additive 增加 `grantRequestPolicy`；缺失时按默认策略补齐，不改变已有布尔权限。
- `get_agent_access_settings` 增加 `pendingGrants`、`activeGrants`、`agentInstanceId` 和 `grantRequestPolicy`。
- 新增 `list_agent_access_grants`、`approve_agent_access_grant`、`deny_agent_access_grant`、`revoke_agent_access_grant`。
- 新增事件 `agent-access-grant-requested`、`agent-access-grant-changed`。
- MCP 权限检查从“只读静态配置”扩展为“静态权限 + 有效 lease”。
- 审计新增 `grantId`、`grantSource`、`grantScope`、`grantExpiresAt`。
- 审批必须支持 sidecar 等待桌面端决定；不能要求 Agent 通过自然语言转述“用户已批准”。
- 重放授权必须校验 `actionFingerprint`；不能只校验 host、方法或 sessionId。
- 重放请求 card 的范围来自先读取的 session summary；实际 host、path 与最终方法必须进入 `scope`，会话不存在时不创建 pending。
- 多能力动作按缺失能力各创建一个 grant；桌面端按能力匹配，不让其他能力的 grant 使校验整体失败。
- `ConsumeAgentGrant` 必须再次检查当前请求策略；`ask` 改为 `deny` 或接入关闭后，既有 grant 也不能继续消费。
- `readSessions` 不接入临时授权；UI 只显示两态，配置归一化时把旧 `ask` 强制改为 `deny`。
- 自动化授权必须包含 `resourcePolicy`，并区分 `ephemeral` / `persistent` 与清理责任。

### 9.4 兼容与迁移

- `agent-access.json` 版本保持向后兼容；新增字段必须 additive。
- 旧版应用读取新版配置时忽略未知字段，但不能因为未知 grant 文件拒绝启动。
- 应用退出时清理所有临时 grant；重启后不恢复 `active` 状态。
- 静态权限永不因 grant 审批而自动修改。
- Agent 的 `APPROVAL_REQUIRED` 必须包含可执行的下一步，不能只返回错误字符串。
- 在客户端提供稳定 conversation/task ID 前，不持久化“任务级”字段，也不承诺任务结束自动撤销。

### 9.5 跨平台

- 授权提示必须同时支持 Windows、macOS、Linux。
- 桌面端不在前台时，使用应用内待授权列表和系统通知；系统通知不可用时仍应保留设置页入口。
- 授权卡不依赖 WebView 前台焦点；最小化时也要能持久化 pending 请求。
- 所有路径展示继续遵守单行省略和复制规则。

### 10.1 P0-A：确定性易用性改进（已实现）

任务：

验收标准：

- 未开放能力不出现在可操作权限列表中。
- 当前生效权限和草稿在同一屏内不会混淆。
- 所有危险权限变更都有明确的变更摘要和确认。
- 现有配置加载后不会被静默改写。

### 10.2 P0-B：场景预设与立即收回控制（已实现）

目标：在 P0-A 的清晰结构上增加快捷路径，但不承诺尚未定义的限时授权能力。

任务：

1. 四个模式：仅元数据、只读分析（推荐）、调试与重放、自动化实验；不做“完全控制”模式。
2. 精确匹配现有配置到模式；匹配不到显示“自定义”，不使用“最接近模式”。
3. 连接对话框与设置页共用预设定义；调整模板时明确提示全局影响。
4. Map Local 根目录、代理验证 origin 与具体功能绑定，不做总开关式强制。
5. 立即收回控制：独立 API，立即生效；展示仍在生效的抓包、系统代理、证书、规则和自动化资源，并提供收尾入口。
6. 首次连接流程：无客户端时先连接，再配置权限；首次安装不把证书、抓包、系统代理与删除/用户资源修改捆绑。
7. 测试：预设映射、精确匹配、依赖提示、连接流程、立即收回与副作用可见性。

验收标准：

- 选择任一模式后仍必须保存，不能静默生效。
- 仅做 Rewrite 或离线验证时不会被要求配置 Map Local 根目录或 origin。
- 只开启代理验证不会被描述成可用的自动化闭环；界面明确依赖 `manageAutomation`。
- 立即收回控制后，所有仍然生效的副作用都可见，并有可执行收尾动作。
- 调整连接模板时，用户能明确知道会影响哪些客户端。

### 10.3 P1：限时授权与审批闭环（首版已实现）

目标：把“预授权未知任务”变成“在具体动作上做一次决定，并让原调用继续”。

实施前置条件（缺一不可）：

- Sidecar 实例 ID 已定义并持久化到 grant 绑定中。
- 授权与具体操作指纹的匹配规则已定义并通过测试。
- 非幂等重放的未知结果处理已定义。
- 授权到期、资源到期和清理责任已分别定义。
- 审批状态机和桌面端全局待授权入口已通过交互评审。

任务：

1. 设计并实现 grant store，绑定 `agentInstanceId`、client name/version、capability、scope 和 fingerprint。
2. MCP 权限检查接入 grant；可临时授权能力映射三态，`readSessions` 只映射 `禁止 / 始终允许`。
3. 新增审批 IPC：sidecar 创建 pending、桌面端批准/拒绝、sidecar 在同一工具调用中继续或返回错误。
4. 全局待授权入口：AppShell 提示、系统通知、设置页历史；不要求用户先进入 Settings。
5. 审批状态机：pending / approved / executing / succeeded / failed / unknown / denied / expired / revoked / cancelled。
6. 重放指纹：sessionId + 最终方法 + 最终 URL + Header/Query/Body 哈希；参数变化重新审批。
7. 非幂等重放只允许一次；未知结果标记 `unknown`，禁止自动重试。
8. 读取范围：sessionId、host + 时间窗口、WebSocket 连接 ID；原始 Body 单独批准。
9. 资源策略：自动化限时授权默认 `ephemeral`；`persistent` 单独批准；授权撤销展示残留资源。
10. 拒绝冷却、重复请求合并、超时/取消语义、审计和跨平台通知。
11. 帮助文档、错误码和排障流程同步。

验收标准：

- 未授权动作返回可机器识别的 `APPROVAL_REQUIRED`，并包含 `requestId`、`agentInstanceId`、`actionFingerprint`、范围和下一步。
- 用户在桌面端批准后，原工具调用继续执行；用户不需要回到聊天重复确认。
- Agent 无法自行批准、修改或复用不属于自己的 grant。
- 同一 Sidecar 实例的重复请求不会重复弹卡；拒绝后进入冷却，Agent 不自动循环重试。
- 非幂等重放在参数变化、未知结果或第二次尝试时重新审批。
- 授权到期后后续调用被拒绝；应用重启后不恢复临时授权。
- 撤销授权后仍生效的资源、抓包、系统代理和证书状态可见，并可收尾。
- 所有批准、拒绝、取消、超时、执行结果和撤销都有审计记录。

### 10.4 P2：策略沉淀与使用洞察

- 按 workspace / 项目保存常用模式。
- 最近 30 天未使用的控制权限提示降权。
- 常用任务的“保存为我的模式”。
- 授权使用统计和异常申请提示。
- 可选的企业策略模板，但不引入云端账号体系。

### 10.5 依赖与风险

| 风险 | 影响 | 缓解 |
|---|---|---|
| 模式映射与实际权限语义不一致 | 用户以为授予范围与实际不同 | 映射表单测 + 保存前显示字段级变更 |
| 授权疲劳 | 用户嫌弹窗多，重新全开 | 合并同类请求、默认一次、常用范围允许 15 分钟 |
| sidecar 与桌面端状态不同步 | 已撤销但 Agent 仍可读 | 每次调用读取 grant store 或短 TTL 缓存，并校验撤销版本 |
| 应用未运行时的授权 | Agent 无法完成审批 | 写工具可拉起桌面端并聚焦待授权；只读工具返回 `APPROVAL_UNAVAILABLE` 和明确下一步 |
| 新权限扩大旧授权 | 升级后能力变多 | 新增权限默认关闭，模式只是草稿，不自动保存 |
| 任务边界无法识别 | 授权被其他对话复用 | 绑定 sidecar 实例；明确“限时授权”限制；未来接入 conversation/task ID |
| 授权到期但副作用仍在 | 用户误以为已经安全 | 授权与资源生命周期分离展示，撤销时提供收尾入口 |
| 资源清理误删用户资源 | 数据损失 | 只清理 Agent 自有资源；用户资源必须单独确认；默认不自动删除 |

## 11. 测试策略

### 11.1 前端

- 模式到权限字段的映射，以及每个字段是否被预设精确包含。
- 当前配置只做精确匹配；自定义配置不被错误归类。
- Map Local 根目录只在选择 Map Local 时校验；代理验证 origin 只在选择代理主动验证时校验。
- 代理验证的依赖提示必须同时说明 `manageAutomation` 与 `manageProxiedVerification`，不能把单项权限描述成完整闭环。
- 保存栏的“当前生效 / 待保存”分离、字段级 diff、高风险确认和未保存离页拦截。
- 立即收回控制后，读取权限仍保留，控制权限立即关闭，临时授权全部清除，并展示副作用清单。
- 连接对话框与设置页使用同一预设定义；调整模板时显示全局影响范围。

### 11.2 Rust / MCP

- 静态权限仍按原语义生效，`grantRequestPolicy` 不改变未授权调用的拒绝路径。
- grant 同时校验 `agentInstanceId`、client name/version、capability、scope 和 `actionFingerprint`；不匹配时不得复用。
- 授权状态机覆盖 pending、approved、executing、succeeded、failed、unknown、denied、expired、revoked、cancelled。
- 同一实例同类请求只产生一个 pending；批准后原调用继续，不需要 Agent 再次调用。
- 拒绝、超时、取消均返回稳定错误码；拒绝冷却期内重复请求不再次弹卡，Agent 不能自动循环重试。
- 批准后参数变化导致指纹不匹配，必须重新审批。
- 非幂等重放的成功、发送前失败、响应丢失三种结果分别处理；`unknown` 不自动重试，再次发送必须重新批准。
- 限时授权到期只阻止后续调用；`ephemeral` 资源按独立 TTL 清理，`persistent` 资源保留到显式回滚或清理。
- 撤销授权后副作用清单完整，抓包、系统代理、证书、规则和自动化资源的状态与权限状态分离。
- grant store 文件损坏、权限不足、应用退出清理、审计脱敏和旧配置兼容。

### 11.3 端到端

- 新用户连接 → 默认只读分析（推荐）→ Agent 查询成功，不需要接触高级权限矩阵。
- Agent 请求读取 Body → 用户批准一次 → 原调用继续并成功 → 下一次请求不作为“最近授权”自动放行。
- Agent 请求非幂等重放 → 用户批准一次 → 发送成功；响应丢失时显示“可能已产生副作用”，不自动重试。
- 用户在另一个对话发起相同调用 → 因 `agentInstanceId` 或指纹不匹配不能复用原授权。
- 自动化实验 → 授权到期后 Agent 无法继续修改资源，但资源仍在生效时持续可见；用户可选择清理 Agent 自有资源。
- 立即收回控制 → 后续控制调用被拒绝，同时仍运行的抓包、系统代理、证书和规则有明确收尾入口。
- 应用退出并重启 → 临时授权不恢复。
- 调整连接模板 → 保存前明确展示会受影响的所有已连接客户端。

## 12. 指标

### 12.1 北极星指标

- **任务完成率**：发起 Agent 任务后，在无需用户改用完整控制的前提下成功完成的比例。
- **每个成功任务的人工打断次数**：中位数与 P90，区分权限审批、参数澄清和失败重试。
- **审批后的恢复成功率**：用户批准后，原工具调用继续并完成的比例。
- **撤销后的副作用可见率**：执行立即收回后，仍生效的抓包、系统代理、证书、规则和自动化资源被正确展示的比例。

### 12.2 护栏指标

- 权限可理解性：用户能够正确说出一组权限会造成的最高风险效果的比例。
- 审批失败率：批准后仍因状态不同步、超时或指纹失效而失败的比例。
- 重复申请率：同一实例、同一动作在短时间内重复弹卡的比例。
- 高风险权限闲置率：30 天未使用但仍处于“始终允许”的比例。
- 残留风险率：授权撤销后，仍有未展示或不可处理的运行时副作用的比例，目标为零。
- 因权限不足导致的任务中断率不应因易用性改造显著上升。

### 12.3 反馈指标

- 权限相关支持问题数量及分类：找不到入口、不知道影响、撤回后仍生效、审批未恢复。
- Agent 权限错误码分布和 `APPROVAL_*` 状态迁移分布。
- 设置页“查看变更”和“高级权限”的使用率，用于判断渐进披露是否有效，不作为成功目标。
- 连接后 7 天内主动降权或撤销授权的比例。

## 14. 待评审问题

已确定，不再作为开放问题：

1. 新配置默认“只读分析（推荐）”；老用户只做精确匹配，匹配不到显示“自定义”，升级不自动扩大权限。
2. 不保留“完全控制”模式；高级区只提供批量选择当前可用能力，并展示字段级 diff。
3. 不承诺“任务结束自动失效”；在客户端提供稳定 conversation/task ID 前，统一使用“限时授权”。
4. 临时授权不跨应用重启保留。
5. 权限撤销与运行时副作用清理分开；撤销后必须展示仍生效对象和收尾入口。

首版已确定的参数：

1. `agentInstanceId` 每个 sidecar 进程生成一次，sidecar 重启或桌面应用重启后旧授权失效。
2. 同一 sidecar 被多个对话共享时，本版接受授权共享；产品不宣称对话级隔离，若需隔离必须由客户端提供稳定 conversation/task ID。
3. 系统代理、根证书和删除会话默认禁止；用户显式改为 `请求时询问` 后可申请，但只提供“允许一次”。`始终允许` 仍需高风险确认。
4. 审批等待 30 秒，sidecar 请求超时 40 秒；拒绝冷却 60 秒；同一实例、客户端、能力与动作指纹的 pending 请求合并。
5. 授权 TTL 与自动化资源 TTL 独立；15 分钟授权不会延长或自动删除持久资源。应用重启会清除 grant，但持久资源仍需显式回滚或清理。

## 15. 最终建议

建议按以下顺序推进：

1. **P0-A 已实现**：能力摘要、隐藏未开放能力、权限分组与折叠、保存反馈、当前生效权限展示。
2. **P0-B 已实现**：权限预设、按功能配置资源边界、统一连接流程、立即收回控制。预设依赖真实有效、精确匹配，全局影响可见。
3. **P1 首版已实现**：限时授权、一次性执行、全局审批、单条撤销、立即收回与实验清理入口均已落地。后续若客户端提供 conversation/task ID，再评估对话级授权与真正的任务结束自动失效。

本方案的长期价值仍是把安全模型从“用户猜着开权限”变成“Agent 说明意图、用户按范围批准、系统按明确规则失效”。但在无法可靠识别任务边界前，产品只能承诺按时间、次数和操作指纹失效，不能宣称已经实现任务级授权。
